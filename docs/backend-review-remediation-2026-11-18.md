## 3. 资金、时间与履约正确性

### FIX-001：上游到期时间丢失时区，可能提前八小时暂停

**问题与证据**

[ZjmfFinanceDriver::syncInfo()](../app/Drivers/Upstream/ZjmfFinanceDriver.php) 将 Unix 时间戳转成 UTC 后调用 `toDateTimeString()`，输出不带时区；[ApplyInstanceSnapshotAction](../app/Actions/ApplyInstanceSnapshotAction.php) 和 [ExecuteServiceTaskAction](../app/Actions/ExecuteServiceTaskAction.php) 又使用默认上海时区解析。

离线 Carbon 复现：时间戳 `1794974400` 应为上海时间 `2026-11-18 12:00:00`，却被解析为 `04:00:00`，偏移 `-28800` 秒。生命周期调度及执行前复验均使用这条错误路径。

**修复方式**

1. 驱动输出带明确偏移的 ISO 8601 时间，例如 UTC 的 `...Z` 或 `...+00:00`，保留真实瞬时值。
2. 统一所有快照消费端的解析方式；写入现有无时区数据库列之前，转换成项目约定的存储时区。不能只修驱动而遗漏 Eloquent 写库及重读后的时区语义。
3. 核对新购同步、回调同步、续费前后同步、暂停及恢复判断，确保比较的是同一瞬时值。
4. 对既有实例通过认证上游只读重查到期边界，生成差异清单后修复；不要给所有历史时间机械增加八小时，因为并非所有来源都是 Unix 时间戳。
5. 对已生成的续费账单、暂停任务分别核对其到期边界。取消失效操作并保留审计；已付款账单不能通过直接改金额或重建任务处理。

**验收条件**

- 上述时间戳经驱动、Action、数据库写入及重读后仍对应北京时间 12:00。
- 覆盖 Unix 时间戳、带偏移字符串、缺失时间及已确认协议支持的无时区字符串。
- 到期前不暂停，到期后才能申请暂停；已续费的旧暂停任务被拒绝。
- 小时、日、月账期及 UTC 幂等边界均保持正确。

### FIX-002：外币账单混用单一钱包，支付币种没有闭环

**问题与证据**

[CreateComboInvoiceAction](../app/Actions/CreateComboInvoiceAction.php) 只检查报价与商品/实例币种相同，却直接使用没有币种维度的 `users.credit`。退款、迟到支付和超额支付也会向该钱包入账。[EpayGateway](../app/Drivers/Payment/EpayGateway.php) 未拒绝不支持的账单币种。

隔离复现：USD 10.00 商品可消耗 10.00 钱包余额并成为 Paid。

**修复方式**

1. 当前推荐采用“钱包与现有易支付仅结算 CNY”的最小方案，明确记录该约定；完整多币种钱包另行设计，不引入隐式汇率。
2. 在创建账单、发起支付和网关适配器中检查支持币种；新购、续费、升级都必须覆盖。限制应在冻结余额及创建支付请求前生效。
3. 同步核对钱包退款、佣金转钱包、迟到付款、重复付款和超额付款的币种边界，不能只拦新订单。
4. 对历史非 CNY 账单先形成核对清单。已收款回调仍须保存验签、去重及人工核对证据；其业务处置需要明确决策，不能盲目兑入 CNY 钱包或用持续失败响应诱发网关无限重试。涉及新 outcome 时先批准枚举及决策表变更。
5. 历史余额无法仅凭当前数值还原币种，必须按账单及流水追溯，不能自动按 1:1 转换。

**验收条件**

- 非支持币种的新购、续费、升级在资金变化前被拒绝，且不请求易支付。
- CNY 纯钱包、组合支付、零额支付及退款保持原金额恒等式和唯一流水。
- 历史外币回调不会污染钱包，重复回调不会造成第二次资金影响。

**决策与当前边界**：C20 已批准且完成上述单币种实现与隔离验收，见 [验收记录](backend-fix002-currency.md)。生产历史外币款项仍须逐单核对，不自动退款、解冻或兑换。完整多币种钱包不在本次授权内。

### FIX-003：履约回收反复延后任务，未执行也可能耗尽次数

**当前状态**：C21 已批准，实现及隔离验收完成；下文保留修复前证据，现行为及限制见 [验收记录](backend-fix003-fulfillment.md)。

**问题与证据**

[DispatchStalePendingTasksAction](../app/Actions/DispatchStalePendingTasksAction.php) 对到期 pending 任务执行 `attempts+1` 并重新设置未来的 `available_at`；[ExecuteFulfillmentTaskAction](../app/Actions/ExecuteFulfillmentTaskAction.php) 因时间尚未到直接退出。实际失败也会增加 attempts，造成双重消耗。

真实 Action 的隔离复现中，调度回收先于 worker 执行，五次预算全部耗尽并变为 failed，驱动执行次数为零。现有 INV-T2 本身也规定回收增加次数，因此必须先统一设计语义。

**修复方式**

1. 先定义 attempts 为“worker 成功认领一次执行尝试”的计数，并明确进程崩溃也会消耗该次尝试；在认领事务中增加一次，结果处理及回收不重复增加。
2. 对仅等待执行的 pending 任务，回收只负责补派发，不修改已经到期的 `available_at`，不消耗执行次数。
3. 对过期 running 租约，核对绑定、付款状态及远端意图后释放租约，按已发生的执行尝试设置退避；远端结果不确定时保留消歧路径，不能自动再次采购或付款。
4. 可重试失败提交新的 pending 状态及退避时间后，通过 `afterCommit` 派发延迟任务；保留补派发扫描作为队列投递失败的恢复手段。
5. 对补派发采用必要的短期去重，worker 仍以数据库状态及租约保证单任务执行；若增加派发时间字段，应先批准 schema 变更。
6. 同步 INV-T2/T3、框架队列 tries 与业务 max_attempts 的职责、人工重试规则和相关测试。不要批量重置已有失败任务，先核对其远端副作用。

**验收条件**

- 复现“调度先执行、worker 后执行”时，任务仍可被认领；反复补派发不会消耗执行预算。
- 默认五次预算对应最多五次认领尝试，可重试失败每次只计算一次。
- 并发 worker、租约过期、旧结果返回、退款及热切换时均不会重复交付或重复采购。
- 达到上限进入 failed 并可被运营发现；人工重试必须保留授权、原因与审计。

### FIX-004：新购缺少请求幂等，重复提交重复扣款

**问题与证据**

[CheckoutController](../app/Http/Controllers/CheckoutController.php) 未接收购买请求标识，[CreateComboInvoiceAction](../app/Actions/CreateComboInvoiceAction.php) 每次生成新账单。隔离复现：相同参数执行两次，钱包 100→80，创建两份账单、实例和任务。

**修复方式**

1. 每次购买意图由页面生成稳定请求标识，重复点击和网络重试复用；用户明确发起第二次购买时生成新标识。按钮禁用只改善体验，不能替代服务端幂等。
2. 持久保存用户作用域的购买请求键，并建立数据库唯一约束；存储位置及新增索引需要设计批准。
3. 在已有用户行锁及账单事务中，先查相同请求。相同规范化业务参数返回原账单；同键修改商品、周期、配置、优惠券或支付选择时拒绝。
4. 首次创建保存可信报价快照；重复请求不能因商品调价生成另一份账单。参数指纹避免保存明文密码等敏感输入。
5. 修复已有重复订单需逐单核对付款及交付，不自动合并或删除账单，也不回收已售卡密。

**验收条件**

- 并发相同请求只有一份账单、一次余额变化及一份交付任务；MySQL 8 并发验证不能由 SQLite 顺序测试替代。
- 同键不同参数被拒绝；新键可以合法再次购买相同商品。
- 覆盖纯钱包、组合支付、零额订单及响应丢失后的重试。

## 4. 业务恢复与页面可用性

### FIX-005：续费单过期后缺少恢复路径

**当前状态**：C23已批准，实现及隔离验收完成；下文保留原审查证据。现行为、Gate及部署/供应商边界见[验收记录](backend-fix005-renewal-recovery.md)。

**问题与证据**

[CreateComboInvoiceAction](../app/Actions/CreateComboInvoiceAction.php) 按账期返回既有账单，不区分是否 Expired；[InitiatePaymentAction](../app/Actions/InitiatePaymentAction.php) 拒绝过期支付。[C14 决策](classic-zjmf-expansion-decisions.md) 已明确要求另行设计恢复策略。这是已知未完成闭环。

**修复方式**

1. 先确定“原账期事件＋显式恢复单”的协议，原过期账单保留终态；恢复单关联原账单、实例及认证后的到期边界。
2. 在用户、账单、实例锁及持久唯一约束下，保证同一账期不会同时存在两份可结算的有效续费请求。不能只给原 billing_period_key 拼随机后缀绕过约束。
3. 恢复时重新核对远端状态、到期边界、配置和价格，向客户明确新金额。原单已解冻的钱包需要按新授权重新处理，不能沿用旧冻结。
4. 原单迟到支付仍按已批准的迟到付款规则处理；恢复单与原单分别去重，不自动把旧付款解释为新授权。
5. 提供客户入口及有权限的运营核对入口；处理已经续费、已终止、存在未决上游付款等情况。

**验收条件**：过期后可以合法恢复续费；原单保持终态；重复恢复、并发付款和旧单迟到回调不产生两次续费或双重扣款。

**裁决结果**：C23已获人工批准，新增两列前驱关系及定向INV-K1规则；不包含现有数据库迁移或真实供应商续费。

### FIX-006：机器命令未决后缺少人工核对恢复入口

**当前状态**：已实现并完成隔离验收。现行为与人工证据/供应商协议限制见[验收记录](backend-fix006-machine-reconciliation.md)；下文保留修复前审查基线。

**问题与证据**

[ExecuteCustomerPowerCommandAction](../app/Actions/ExecuteCustomerPowerCommandAction.php) 将 requested/unknown 作为后续命令阻断条件；[机器管理说明](classic-zjmf-machine-controls.md) 明确没有交付人工消歧界面。热切换也需要核对旧绑定遗留的 cloud_operation。

**修复方式**

1. 增加受权限控制的人工核对 Action 和管理入口，显示原请求标识、命令、绑定及脱敏证据。
2. 事务外查询上游可证明的状态，再在锁内核对请求与当前绑定。证据不足时维持 unknown；尤其重装、重置密码等不能仅凭电源状态判断完成。
3. 核对结论应关联原请求，记录操作人、原因、证据及处理前后状态；恢复新命令权限不等于重放原命令。
4. 热切换时将旧操作按旧绑定归档保留，明确新绑定的操作状态；旧请求稍后返回不得覆盖新绑定。

**验收条件**：模拟超时及进程中断后可进入核对流程；不能一键盲目清除标记；重复确认幂等；越权拒绝；旧绑定结果不能恢复或改写新绑定操作。

**实施判断**：复用现有权限、JSON与审计结构，不改冻结状态；机器可查询现状仅作辅助，任务完成依赖有来源的人工核对。原请求仍不得重放；无证据则保留阻断。详见验收记录。

### FIX-007：报价、机器控制、账户验证共用限流桶

**问题与证据**

[routes/web.php](../routes/web.php) 对多项业务使用没有业务前缀的数字 throttle；当前框架认证请求按用户 ID 生成键。真实中间件复现：十次报价后，第一次电源查询返回 429。

**修复方式**

1. 按报价、机器查询、机器命令、邮件验证、短信验证、OAuth 等业务定义独立命名限流器，键中包含业务名称及用户或游客标识。
2. 对必须共享的额度显式记录共享范围；不要通过统一放宽所有限额掩盖互相干扰。
3. 同步前端对 429 的提示，读取 Retry-After，避免自动请求在限流后持续重试。

**验收条件**：一个业务用尽额度不消耗其他业务额度；各自超限仍返回 429；同一用户多标签页及游客同 IP 的实际规则符合设计。

### FIX-008：后台编辑文章切换栏目导致 404

**问题与证据**

[CMS 编辑表单](../resources/views/filament/pages/cms-content.blade.php) 允许选择其他栏目；[SaveCmsArticleAction](../app/Actions/SaveCmsArticleAction.php) 却按原文章 ID 与新栏目 ID 联合查询。隔离复现得到 ModelNotFoundException，对应 HTTP 404。

**修复方式**

1. 推荐本轮保留现有“不跨栏目替换文章”的行为：编辑时锁定原栏目，新增文章才提供完整栏目选择。
2. 服务端对现存文章提交不同栏目给出明确的字段校验错误，而非通过 firstOrFail 返回含糊的 404；不存在的文章及无权访问仍按各自约定拒绝。
3. 如果产品决定支持移动，应另行设计源/目标栏目权限、slug 冲突、旧 URL 处理和审计，再实现专用移动流程，不能直接删除栏目约束。

**验收条件**：正常编辑不再展示无法完成的操作；手工篡改栏目返回可理解的校验错误；已有文章不会被跨栏目覆盖。

### FIX-009：既有栏目类型可修改，与文档约定冲突

**问题与证据**

[CMS 说明](cms-storefront.md) 写明不允许改变既有分类类型；[SaveCmsCategoryAction](../app/Actions/SaveCmsCategoryAction.php) 与后台实际允许 news 改为 help，导致整栏文章旧 URL 失效。

**修复方式**

1. 推荐保持既有类型不可变：编辑时展示固定类型，服务端拒绝修改 type。
2. 盘点已发生的类型变化及旧链接。如果确实需要转换，应单独设计 URL 迁移和重定向，保留同类型 slug 唯一约束。
3. 同步文档、界面与测试对“栏目类型不可变”或“受控转换”的统一约定。

**验收条件**：普通编辑不会改变整栏路由前缀；手工提交 type 不能绕过约束；同 slug 的 news/help 两个栏目仍可合法共存。

## 5. 上游调用、调度与通知

### FIX-010：面板登录与监控互相加载

**问题与证据**

[OpenInstancePanelAction](../app/Actions/OpenInstancePanelAction.php) 登录时未指定 login_form；[ReadInstanceTelemetryAction](../app/Actions/ReadInstanceTelemetryAction.php) 读取监控时未指定类型。因此走 [ZjmfPanelProtocol](../app/Drivers/Upstream/ZjmfPanelProtocol.php) 全量分支。离线客户端替身复现一次读取产生七次串行请求，登录内容失败还会丢弃已取得的监控。

**修复方式**

1. 登录仅请求 login_form；监控仅请求 machine_status/chart；复用已有类型选择参数。
2. 各图表失败返回对应不可用状态，保留成功数据。主机认证及所有权核验失败仍应中止整个读取。
3. 保留请求前后实例绑定复验。不要以缓存登录令牌、保存远端 HTML 或移除授权检查换取速度。

**验收条件**：登录不请求图表或电源状态；监控不请求登录 HTML；单图失败不遮蔽其他图；实例读取期间被重绑定时拒绝返回旧数据。记录修复后的请求数量及隔离耗时。

### FIX-011：全量同步阻塞分钟调度

**问题与证据**

[ProcessInstanceLifecycleAction](../app/Actions/ProcessInstanceLifecycleAction.php) 在判断提醒窗口前逐台同步，窗口内又可能经续费入口重复同步。[调度定义](../routes/console.php) 串行运行；[systemd service](../deploy/cloudcms-schedule.service) 为 oneshot、无启动超时上限。

按当前 timer 方案，一百台服务各等待三秒，一轮可能占用约五分钟，并延误之后的分钟任务。这是静态成本推导，不是生产压测结果。

**修复方式**

1. 将调度器改为有界候选扫描和任务派发，各实例同步在独立队列任务执行，按实例防重入并限制并发。
2. 分开“全量状态对账”和“临近到期操作”：全量对账轮转处理且有明确时效，临近到期候选优先处理。不能只按本地日期过滤而完全取消全量对账，因为本地到期时间可能已过时。
3. 同一轮尽可能复用认证快照，续费账单查重和预同步顺序减少重复 I/O，同时保留状态变化及有效期校验。
4. 保留 withoutOverlapping/onOneServer；明确派发任务的超时、租约和队列 retry_after。简单增加 runInBackground 不能替代受控并发及去重。
5. 验证 timer 部署方式下，供应商缓慢时账单过期、回收及佣金任务仍可按预期频率运行。

**验收条件**：使用模拟上游延迟验证批次有界、任务无重复；记录总实例量、候选量、请求数、调度耗时和处理延迟。生产时效目标需在实施前确定，不能仅以一次命令成功作为验收。

### FIX-012：通知失败未重试，模拟通道误记送达

**问题与证据**

[SendNotificationJob](../app/Jobs/SendNotificationJob.php) 配置三次重试，但 [SendLifecycleNotificationAction](../app/Actions/SendLifecycleNotificationAction.php) 捕获失败后正常返回。隔离 worker 复现：发送失败后 jobs 清空、failed_jobs 为零，仅产生失败通知日志。旧分支使用 log 邮件通道时记录 sent，与新事件通知的 simulated 不一致。

**修复方式**

1. 区分发送成功、模拟发送、永久拒绝、可重试临时失败和结果不确定。先记录脱敏失败证据；仅对按协议可重试的失败抛出队列可识别异常或显式释放任务。
2. 明确三次尝试及退避语义，统一旧续费通知与新事件通知的失败处理。
3. log 邮件/短信只能记录 simulated；只有真实传输协议确认接受才记 sent，且不把 accepted 描述成用户已阅读。
4. 外部发送后进程中断存在重复发送窗口。能使用供应商幂等标识时复用；没有相应协议时记录可能重复的边界，不承诺 exactly-once。
5. 最终失败进入可检索的失败记录及人工处理入口，避免只在普通日志中留下不可操作的 warning。

**验收条件**：模拟临时失败后成功、永久拒绝、超时不确定及最终耗尽；计数和状态准确，渠道彼此独立，模拟发送不会显示 sent，凭据不进入日志。

### FIX-013：一个商品失败中断目录同步批次

**问题与证据**

[ProbeClassicCatalogAction](../app/Actions/ProbeClassicCatalogAction.php) 只捕获 DomainException，而 [ZjmfPurchaseProtocol::configuration()](../app/Drivers/Upstream/ZjmfPurchaseProtocol.php) 的配置读取失败抛出 ValidationException，可能中断后续商品及供应商。

**修复方式**

1. 在单商品同步边界处理预期的业务校验失败，记录商品、供应商、错误类别及本轮失败数量，然后继续其他商品。
2. 在供应商探测边界处理该账号整体不可用；不要让单个商品失败跳过同账号其他可同步商品。
3. 未知程序错误仍暴露为真实失败，不能使用空的 catch Throwable；日志避免带入密码、自定义字段和原始敏感响应。

**验收条件**：第一件商品配置失败时，第二件及其他账号仍完成；失败商品不留下半更新配置；结果汇总区分成功与失败。

## 6. 页面性能与内容查询

### FIX-014：摘要生成反复解析完整正文

**问题与证据**

[CmsRenderer::excerpt()](../app/Support/CmsRenderer.php) 为截取约 160 字先执行全文 Markdown 解析和 HTMLPurifier；[文章卡片](../resources/views/public/partials/articles.blade.php) 在 SEO 描述为空时逐篇调用。详情缺省摘要还会再次净化正文。

纯 PHP 进程基准：六次摘要调用，约 10KB 正文合计 148.7ms、100KB 合计 1109.8ms、500KB 合计 6046.6ms；最后一档峰值内存分配约 94MB。这不是 HTTP 响应耗时。

**修复方式**

1. 优先复用已填写的 SEO 描述；缺省摘要可在保存后生成，或按正文内容版本缓存，缓存失效应覆盖正文、格式及相关渲染规则变化。
2. 本轮若不新增字段，可使用可失效缓存减少重复工作；持久摘要列属于需批准的 schema 方案。
3. 列表不再逐请求全文净化长文。详情页复用本次已渲染的安全 HTML 生成摘要，避免同一正文处理两遍。
4. 保留正文输出的安全净化。摘要必须作为纯文本转义，不能为了速度直接输出未清洗 HTML。

**验收条件**：在相同正文样本下记录冷/热缓存耗时、峰值内存及净化次数；热列表不再逐篇净化全文；更新后立即使用新摘要；HTML/Markdown/XSS 回归均通过。

### FIX-015：sitemap / llms 索引加载全部文章正文

**问题与证据**

[PublicContentController::sitemap()/llms()](../app/Http/Controllers/PublicContentController.php) 对全部公开文章执行无字段投影的 get，实际输出只需 URL、标题及更新时间。已确认查询结构，未做生产规模内存压测。

**修复方式**

1. 仅选择 ID、栏目关联键、slug、标题及必要时间字段，关联栏目也投影必要字段；保留 published/visible 过滤。
2. 使用分块或流式遍历，并同步改造输出，避免虽然改成 cursor 却又把全部模型或正文攒入数组。
3. 对确实达到协议规模上限的站点再做 sitemap 索引/分片；字段投影应先修复，不以分片未实现为由保留正文读取。

**验收条件**：查询不包含 body、description 等无关大字段；草稿、隐藏和预约文章不泄漏；大样本下记录峰值内存，输出 XML/文本及 URL 完整正确。

### FIX-016：客户总览全量加载并输出所有商品

**问题与证据**

[CustomerSalesController::index()](../app/Http/Controllers/CustomerSalesController.php) 对全部可售商品 get，[客户总览](../resources/views/sales/console.blade.php) 随商品数增加输出购买内容。普通客户入口因此承受全目录规模。

**修复方式**

2. 投影展示必要字段，避免把完整商品配置及价格 JSON 全量读入总览。
3. 商品详情和下单继续执行服务端可售性、权限及可信报价校验。

**验收条件**：大量商品时总览读取和输出数量有固定上限；其他商品可通过商城分页访问；隐藏商品、停用供应商及本人数据权限不回退。

### FIX-017：规范、交付说明与实现状态不同步

[工程章程](../CLAUDE.md) 的部分阶段描述仍以 Filament 多面板客户控制台及计划驱动为目标；[候选版本说明](release-0.1.0-rc.1.md) 已明确客户门户为 Blade、部分能力延期。此前的“Specs 清空”也不能证明所有阶段能力已交付。FIX-009 是具体的规则与实现冲突。

**问题与依据**：[AffiliateFunds::hasReceivable()](../app/Services/AffiliateFunds.php) 按历史追回流水中的正应收判断阻断；现有规则明确没有自动清偿，后续正余额也不会解除该阻断。

**修复方式**：先批准可接受的清偿来源及授权；新增可追溯的清偿记录关联原应收，原 financial_transactions 保持追加式不可改写。按“原始应收减已确认清偿”计算剩余应收，处理部分清偿、重复提交及错误清偿冲正。不能直接把历史 meta 中金额改成零，也不能未经授权扣普通钱包。

**验收条件**：未清偿仍阻止提现；部分/全额清偿金额准确；重复操作不重复收款；并发提现与清偿串行核对；原始追回证据始终可查。

### FIX-023：通知缺少持久事件 outbox

**问题与依据**：[NotificationManager](../app/Services/NotificationManager.php) 在提交后派发通知；[版本说明](release-0.1.0-rc.1.md) 明确无持久事件 outbox。数据库已提交而通知未进入队列的故障窗口缺少恢复来源。

**修复方式**：在 FIX-012 后定义业务事件唯一键及持久事件表，在业务事务内记录事件；独立派发器扫描并按事件/渠道/接收者去重生成发送任务。分别保存派发和发送结果，队列丢失可从持久事件恢复。实际外部送达是否可去重取决于供应商协议，不能仅凭本地唯一键承诺全链路 exactly-once。

**验收条件**：业务提交后派发前崩溃、队列不可用、重复扫描及发送后进程中断均有可追溯处理；正文和事件载荷不保存密码、卡密及不必要的个人信息。
