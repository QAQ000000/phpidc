# 机器资源读取与下单核价性能修复

日期：2026-11-19（Asia/Shanghai）。本记录覆盖现有预览的只读性能定位、传输并发、渐进监控与核价交互修复。代码、真实浏览器及完整门禁已通过；保留中间失败样本和供应商自身延迟。

后续：用户已采用[本地配置预估与提交价格确认](local-quotation-checkout-confirmation-2026-11-19.md)。本文实时报价耗时保留为前一阶段验收；当前配置预览改为本地计算，最终提交仍实时核验。

## 实际原因

预览原由单个 PHP 内置服务进程处理 HTTP。监控读取占用该进程时，即使不访问上游的 `/up` 也要等待：本轮原监控 POST 用时 38.255 秒，同期 `/up` 用时 37.928 秒。监控的 header、STATUS、CPU、disk、memory、flow 先后等待上游，各次约 2.5–10.2 秒，叠加为整个页面的阻塞。

购买预览报价另有三个串行远端调用：`GET /user_info` 取得账户货币、`GET /cart/stock_control` 验证隐藏/库存、`POST /cart/get_total` 核价。基线三次分别 1270、1173、1206 ms，客户请求总计 3.901 秒。配置页本身仅 0.205 秒，主要等待发生在远端接口。

参考项目 `/www/wwwroot/zjmf-manger-decoded` 仅作源码对照，没有修改或运行其业务代码。其购物车 `configureproduct.js` 调用订单摘要，`CartController::getTotal` 使用商品、价格与配置快照计算；`currencyPriority` 的缺省处理不能替代本项目已验证的显式账户货币和实时库存规则。机器状态/图表独立读取也说明，操作入口不应依赖所有监控都完成。参考实现不构成跳过本项目财务和权限边界的依据。

## 已实施的运行与请求修复

- 预览沿用 PHP `/www/server/php/84/bin/php`、原端口 `127.0.0.1:59493`、数据库、storage、APP_KEY、账户与会话环境，改为 `PHP_CLI_SERVER_WORKERS=4`。新父进程 `1728214`，四个子进程 `1728216`–`1728219`。这是本地预览并发，不替代生产 PHP-FPM 部署。
- `ZjmfClient::readBatch` 只允许白名单独立只读请求，最多同时四个；账户鉴权共用，405 只重新鉴权一次并重放失败的读。创建购物车、支付、续费和机器写操作不能进入批次。每个请求仍独立脱敏记录，连接/非 200/非 JSON 失败保持可见，非连接类程序异常继续抛出。
- 核价的账户货币和库存检查并发，随后使用明确 `currencyid` 调用实时 `get_total`。每次仍重读货币、隐藏/库存、价格和开通费；不缓存报价，也不采用客户提交的金额。
- 配置输入合并为最多一个在途请求和一个最新候选，250 ms 合并输入。输入变化立即使旧结果失效；重复点击复用同参数在途请求，完成后的显式点击仍重新取价。手动报价原地更新，保留无 JS 的表单回退；请求只携带 CSRF、计费周期与配置，不传无关主机密码、购买请求键或钱包/网关字段。
- 创建账单继续实时校验上游主机名/密码规则并重新核价；报价预览约两轮网络请求，实际创建账单另有配置规则请求，不能把预览结果直接作为购买授权。资金锁、账本、购买幂等与上游支付链保持原规则。

监控聚合请求也已改为有界并发；它仍会等待本批最慢的一项，因此默认入口改为先返回本地页面，再逐项读取电源状态及每张图。GET `/console/instances/{id}/telemetry` 不访问上游；脚本最多同时发起三张图和一个状态请求，完成一项显示一项。单项失败立即清除旧数据，保留手动重试，不自动轮询；原聚合 POST 保留为无 JS 回退。

每张图只读取对应的认证上游接口，不再重复读取 header。与既有独立 STATUS 查询一样，只有原实例已认证同步的图表能力可以开放数据读取；网络前后仍核对本人、Active、绑定、账户启用、端点与鉴权指纹。各图共用一个服务端验证的最近 24 小时窗口，结束时间须在最近五分钟；失效后刷新页面。内部读取选项通过具体类传递，没有改变公共能力接口或 DTO。机器管理与所有实际机器变更继续使用实时 header 复验。
