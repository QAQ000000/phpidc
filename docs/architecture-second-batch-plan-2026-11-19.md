# 架构审计第二批：业务状态与审计分离

基线：`7aab103`。用户指示“可以开始第2批”，并明确选择“采用 B2-01 两列最小方案（推荐）”。两个新增字段及对应历史兼容契约已批准；沿用验证后自动提交、必要预览迁移授权。

## 已核实的问题与本批范围

1. `PaymentAttentionCases::assertCallbackSource()` 依赖原 `payment.callback.attention` 审计，审计缺失会使合法补记失败，已结案记录也可能重新判为未结。
2. `hasUnresolvedForUser()` 用审计发现未登记的历史关注。不能直接移除此查询，否则会漏掉历史注销阻断。
3. 零佣金**结转**完成事实目前只在 `affiliate.zero_accrual` 审计中。审计缺失后，维护重新选中、重复核算，推荐人的注销可能再次被阻断。本次未证实重复支付；该分支不生成佣金、资金流水或通知。

本批只迁移上述支付案件核验、零佣金结转及注销/维护消费端。机器操作核对、应收人工复核重放、安装恢复等剩余审计依赖另列后续；本批完成不表示允许清空或归档全部审计。

## 推荐决议 B2-01：复用业务表，仅增两列

| 表/字段 | 类型 | 业务含义 |
| --- | --- | --- |
| `reconciliation_cases.source_snapshot` | nullable JSON | 原支付关注来源的非敏感事实快照：version、callback_id、invoice_id、user_id、reason、outcome、amount、source_fingerprint。仅支付回调来源使用；其他来源保持 NULL。 |
| `invoices.affiliate_zero_accrual_at` | nullable timestamp | 原账单已按其金额及原推广快照完成核算，结果舍入为零。它是核算结果，不是付款、退款或佣金金额。 |

不新增案件表、通用事件框架、佣金状态或零额佣金行；不改 `line_items` 原始快照、历史金额或资金流水。原审计仍在同一事务正常写入。

### 支付来源校验与历史兼容

- 新案在原财务事务内保存来源快照，读取时与原回调、原账单、案件身份/指纹逐项比对；原业务权限、原身份与原收款唯一键保持。
- 历史案仅以完整匹配的原审计补空快照；已有快照不覆盖，矛盾证据拒绝。只有 reason、缺字段或损坏证据不能被当前回调“补造”为已验证来源。
- 新增来源列的同一条迁移内分批登记所有 audit-only 历史关注，并检查旧兜底范围零遗漏，迁移成功后才开放新代码业务读取。可识别原主体但缺证明的记录保持未结、来源快照为空；无法关联或矛盾数据明确报告，不能把失败当成“无未结”。停稳旧写入后执行；MySQL DDL 不能整体回滚，因此字段与历史转换允许失败后安全重跑。
- 不向已结案案件末尾追加普通来源处置记录，避免破坏“最新处置为 resolved 且 sequence=revision”的既有结案证据。补来源不改案件版本、终态或处置顺序。
- 历史审计读取仅保留在显式升级/回填路径；当前业务读取不依赖审计存在。

### 零佣金完成事实与历史兼容

- 在原用户升序锁→账单锁内，保留 Paid、新购、CNY、非自荐、付款时间、账户及原快照校验，再通过 `Money::percentOf()` 核算。结果为零时写完成时间及原审计，同事务回滚；重复调用从业务字段返回，不重复写审计。
- 注销及维护只读该完成字段。正佣金结转/成熟及应收版本规则保持；0 commission 行、0 ledger、0通知的原零佣金契约保持。
- 历史完整匹配的零结转事实可回填；缺证据或矛盾不标完成，由原正常结转流程重新核验。不得为了回填调用非零结转或触发资金/通知。

## 验收与实施边界

- 支付新案与合法旧案补源后，在隔离库移走对应审计，补记、结案、重放及注销判断保持；篡改来源、缺证据或未结案仍拒绝。
- 零佣金完成后移走审计，维护不重选，注销不误阻断；重复调用、舍入边界、正佣金、审计/业务写故障原子回滚通过。
- 历史升级重跑幂等，保留原回调、账单、案件版本/处置及原行数据；测试包含 audit-only、缺失、损坏和矛盾证据。
- 允许将旧测试中“升级后临时插入 audit-only 表示当前业务状态”的夹具改为持久来源/案件，保留全部严格阻断和财务断言；另以真正旧 schema 的升级场景继续验证 audit-only 历史兼容。Specs 不修改。
- 完整 Pest、PHPStan、Pint、语法检查通过后分别提交支付来源与零佣金改动；原预览迁移前备份，迁移后核对原数据及健康页。
