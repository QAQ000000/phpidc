## D01：钱包主动充值

推荐：复用已有 `InvoiceType::WALLET_TOPUP` 和 Epay 支付尝试/验签；仅 **CNY 1.00–10000.00**，外部网关全额付款，无优惠券、分佣或钱包支付。增加独立 `topup_request_id` 及用户作用域唯一索引，不挤占新购请求键。充值单没有产品/实例/履约任务，定向澄清 INV-I4、P8 和金额写入者边界。

服务端校验申请金额并保存固定快照；金额不可在付款或回调时由客户端重新指定。回调按已核验实收处理：同一真实交易只记一次；足额入钱包，超额或第二笔不同真实交易、过期迟到款按既有规则记账并告警；短款不累计，保留人工核对。

若完整实收金额会使余额列溢出，保存原验证回调及 `wallet_capacity` 对账原因，拒绝全部自动入账并持久告警，提交后 ACK；不部分入账、不删除回调重新收款。后续人工补偿另按原回调唯一核对，不提供任意调账入口。字段、快照和结算矩阵见 [钱包充值提案](wallet-topup-proposal-2026-11-18.md)。

**首期禁止充值走普通商品退款。** 已到账充值再执行 `refund_wallet` 会重复增加钱包，`external_record` 也不能跳过钱包扣回。充值资金退回需要独立的可用余额/冻结和外退协议，本次不开放该入口。

## D02：注销匿名化

推荐：仅本人当前密码确认并勾选不可逆确认。钱包/冻结钱包/可用及冻结佣金非零、待成熟佣金、未结账单、未终止服务、未决任务/提现/工单、未清偿应收等均阻断；不提供管理员强制清零或没收余额。成功后软删除，匿名化当前身份资料、撤销登录及身份/通知绑定，保存财务、履约、审计和幂等关联。

推荐释放原邮箱、手机号和 OAuth 标识，允许重新注册/绑定；新用户 ID 不继承任何旧账务、服务或凭据。若需永久禁用原身份，需另定身份指纹及密钥/保留策略。

注销无法排除多年后收到原账单的有效付款。回调须按原用户 ID（含软删除用户）执行原财务决策、保存唯一账本并告警人工清退；不得复活账户、发货或转给同邮箱重新注册的新账号。未发送通知在发送前检查注销状态并取消；已发往供应商的请求不能宣称已撤回。匿名化字段、历史存档保留范围见专项提案。

本轮匿名化覆盖**账户认证和联系资料**；财务、支付、履约/交付、已关闭投诉及审计的历史证据按原受限权限保留，不宣称全库历史个人数据或供应商资料已删除。通知目标字段另行匿名化并防止旧 Job 回写；具体字段清单、注销阻断和并发规则见 [注销与应收专项提案](account-anonymization-receivables-proposal-2026-11-18.md)。

## D03：外部佣金提现

当前没有已核实的代付供应商协议。推荐首期按 **人工转账、凭证确认** 实现完整闭环：客户申请→独立财务审批→冻结佣金→记录执行意图→财务在系统外转账→核验凭证确认完成。

新增 `affiliate_frozen_balance`；审批只冻结，确认真实付款才消耗冻结金额并记外部 payout 流水。已证明未付款的失败才解冻；结果不明保持冻结并核对原笔，不创建新出款。收款快照加密，外部交易标识唯一，审核/确认/核对分别授权并审计。普通钱包不参与。首期建议 **CNY 1.00–10000.00，商家承担手续费**。

若要求自动代付，请指定供应商及付款/查询/回调/幂等文档；本地流程和模拟测试不能代替供应商对接。具体状态、字段和金额守恒见 [外部提现提案](external-affiliate-payout-proposal-2026-11-18.md)。

## D04：退款应收清偿

推荐首期仅由具有独立 `finance.receivable` 权限的财务人员，登记**已经完成的外部收款**；支持部分清偿、全额清偿及追加式错误冲正。清偿须关联原退款追回流水、CNY 金额、唯一请求/收款凭证、操作人及原因。历史 `financial_transactions` 不改写；原始应收减已确认清偿再加有效冲正得到余额，未清偿继续阻断提现。

不自动扣普通钱包或新成熟佣金；“账户又有余额”不代表清偿。必要增量表、两种账本方向及全局锁序调整作为本次定向批准范围，具体字段见专项提案。冲正导致应收重新出现时，后续提现重新阻断；不回滚已真实完成的外部付款。

一笔应收可多次部分清偿；一次错误冲正完整撤销一笔清偿，再以新的正确登记更正，保留唯一有效凭证和不分叉的修订链。首期一张收款凭证不能同时分配给多笔应收或多个用户。结构和验收见 [应收清偿方案 §4](account-anonymization-receivables-proposal-2026-11-18.md#4-模块二退款佣金应收的外部收款登记与冲正)。

## D05：通知持久事件 outbox

推荐在业务事务内保存带稳定唯一键的安全事件，持久化每个事件/渠道/接收者的投递记录；业务回滚时事件也回滚。提交后派发，定时补扫恢复队列不可用或派发前崩溃；重复扫描不重复生成投递。收件人及模板正文使用事件发生时的受保护快照，发送前再核对订阅和模板启停状态，失效时取消而不改送新地址。

发送前持久化执行意图、核对用户及绑定有效性，使用租约约束 worker；确认未发送的临时失败可退避重试。请求发出后超时、已接受后进程中断等不确定结果保留为待核对，不自动当作未发送重发。供应商不支持幂等时，本地唯一键不保证远端只送达一次。

事件仅携带业务主键及允许的金额/状态变量，不保存密码、卡密、完整收款信息；收件快照受保护，注销前后不得向新注册身份递送旧事件。旧队列不盲目回填或重放，保留兼容处理和核对说明。事件、投递及日志关联的增量结构和相应 Action/Job 契约需定向批准，具体结构和故障窗口见 [通知 outbox 提案](notification-outbox-proposal-2026-11-18.md)。
