## C21 / FIX-003：履约认领计数与补派发

### 状态：已批准，进入实施

用户明确回复“批准 C21，继续 FIX-003（推荐）”；批准范围为下列确定方案及规则/旧计数测试的定向修改，不扩大到 schema、历史批量修复或供应商写入。

现行 INV-T2 与 CLAUDE §3.2 要求 sweeper 每次回收都增加 attempts、重新推迟 available_at；worker 失败又增加一次。清单中的隔离复现证明：调度先于 worker 时，驱动零次执行即可耗尽五次预算。`FulfillmentRecoveryTest` 的过期租约夹具目前 attempts 默认零、回收后期望一，编码了旧规则。按 guardrails §1.1/§4，不能通过偷偷改规范或断言继续实施。

### 已批准的确定方案

1. **attempts 表示 worker 成功认领的执行尝试次数。** 在锁定实例、任务且验证状态/到期时间/绑定/预算后，写 running、worker 和租约的同一事务内增加一次。执行结果或 sweeper 不再增加。认领后进程崩溃也消耗该次；收到重复队列消息但未认领不计数。
2. **到期 pending 只补派发。** 仍按原一分钟扫描门槛筛选；不推迟其已经到期的 available_at，不增加 attempts，不改变未来退避或有效 running 租约。短期 cache 去重只抑制重复投递，失败释放去重标记；数据库行锁/租约仍是认领的唯一权威，缓存丢失不能导致重复执行。不新增列或表。
3. **过期 running 释放旧租约后退避。** 保留已认领次数，按次数取 60/300/900 秒退避（第三次及以后九百秒），提交 pending 和 available_at 后延迟派发。旧 worker 的返回不能通过 worker ID/租约校验，不得提交凭据或状态。同步核对付款/取消及当前绑定；保留现有退款、热切换和远端意图拦截。
4. **最多五次认领。** 第五次允许执行成功；第五次失败或租约过期则 failed 并告警，不得自动第六次。可重试且尚有预算的结果在事务内保存 pending/退避，提交后投递延迟 job；永久失败直接 failed，保留已有实例失败映射和审计。补派发扫描继续补偿投递失败。
5. **队列重投与业务预算独立。** 保留 job timeout=180、租约=210、retry_after=240、框架 tries=3 和 backoff；队列重投必须经过同一数据库认领门槛，不能扩大业务 max_attempts。框架消息失败不直接抹除持久任务，未完成任务仍由 sweeper 在预算内恢复。新增 schema/枚举、改变远端协议不在本次方案内。
6. **不盲目重放上游副作用。** 经典购买仍先对账，续费/升级和 Sub2API 持久意图继续用于消歧；未决请求不能因为租约或框架重投被当作全新采购。人工 retry 仍须权限、原因、审计，显式 reset attempts=0；不批量重置历史失败任务或假定它们从未执行。
7. **定向修改范围。** 批准后澄清 INV-T2/T3、CLAUDE 回收条款及相应 guardrails 批准记录；仅修正明确编码旧计数语义的夹具/期望。例如过期 running 测试应从 attempts=1 起步，回收后仍严格为 1，并增加未执行 pending 不耗预算等行为测试。原资金、幂等、未来退避、有效租约、旧 worker 拒绝、权限和审计断言保留，不修改 Specs。

### 获批后验收计划与保留风险

- 复现调度先执行、worker 后执行；重复补派发始终不耗预算或延后 due，未来任务仍不执行。
- 独立 MySQL 8 双 worker 竞争只认领一次；计数和租约原子提交；第 1–5 次边界、可重试失败、永久失败及崩溃回收均可解释。
- 覆盖租约过期后旧结果返回、退款/热切换、已支付状态变化、经典购买及续费/升级/Sub2API 未决意图，确保不会重复采购或交付。
- 人工恢复保留原因和审计；不自动修正历史 attempts。旧计数无法仅凭当前值还原真实执行次数，应另做历史核对。
- 三道 Gate 全绿后另附验收记录；真实供应商故障、生产队列积压和缓存多节点行为在未实际验证前保持未验证。

### C21 实施结果

已按上述范围完成。全套 **642 passed / 5242 assertions、PHPStan 0、Pint clean**，独立 MySQL 107 项相关测试与多进程竞争、中断恢复通过；没有新增 schema、重置历史任务或调用真实供应商写接口。详见 [FIX-003 验收记录](backend-fix003-fulfillment.md)。扩大 MySQL 探索发现旧目录测试依赖 JSON 键序，保留原断言并另列限制，不冒充全套 MySQL 通过。

## C22 / FIX-004：用户作用域的持久购买幂等

### 状态：已批准，进入实施

已核实：新购 Action 每次生成新 invoice_no，现有唯一 billing_period_key 属于续费/升级事件；HTTP 购买和 Action 都没有购买请求键。用户行锁只能避免余额丢更新，不能区分两次相同请求。根据 guardrails §1.3 和用户关于新增字段先停止汇报的要求，用户已明确批准“批准 C22，继续 FIX-004（推荐）”，覆盖下列方案；既有验收数据库的迁移和历史重复单修复仍不在授权内。

### 已批准的确定方案

1. **仅增加一个可空列与联合唯一索引。** 新迁移为 invoices 增加 `purchase_request_id VARCHAR(26) NULL`，`UNIQUE(user_id, purchase_request_id)`；既有账单和非新购账单保持 NULL，不回填猜测值，不占用 billing_period_key。允许两名用户使用同一请求值，但不能互查或复用对方账单。
2. **所有新购必填 ULID request_id。** HTTP 和新购 Action 均要求输入中携带该字段，不使用服务器为缺失 POST 临时生成新键的降级路径。保持现有 Action 方法签名，通过 input 携带；定向给旧测试/验证脚本的新购调用补充各自固定的测试请求键，既有资金和业务断言不变，不动 Specs。续费/升级现有键协议不变。
3. **每份表单一个稳定购买意图。** 公开商品、本地卡密直购、客户总览、完整配置页面均携带键；重复点击、网络重投、校验错误后的重显及普通实时报价保留同键。用户明确“再次购买”或重新打开一份新表单才取得新键。不会把全局页面缓存或 CSRF token 当作购买键；JSON 客户端自行生成 ULID 并在重试时复用。
4. **请求身份与可信价格分开。** 规范化调用方的商品、周期、选项/自定义字段、主机名/密码、优惠券、use_credit 和 gateway，固定类型、映射排序和空值语义，拒绝不支持的结构。请求身份不包含客户端金额，也不包含商品现价、自动生成密码等后续派生值。同键不同业务参数返回校验错误，不能静默覆盖账单。密码/私密选项不写明文指纹或日志：将带版本号的规范化请求存于 `line_items.purchase.encrypted_request`，比对时解密并计算内存 SHA-256 指纹、用 hash_equals 比较。它不是价格来源。
5. **在副作用前查重，并在创建事务内再次查重。** 当前 HTTP 的商品规则检查及 Action 的实时核价之前先按当前用户/请求键查已保存账单；存在则核对请求身份并返回原账单。首次需要核价的请求保持 HTTP 在事务外；最终事务先锁用户，再查相同请求并核对，确实不存在才沿用现有规则校验、可信报价、冻结/结算、用券、实例/任务写入。联合唯一键为持久兜底，异常不吞掉，不在持锁期间调用供应商。
6. **重试返回原财务事件。** 价格、库存、当前商品规则或优惠券额度后续变化不重建已保存订单；仍核对本人归属及原账单 CNY 边界。Expired/Cancelled/Refunded 保持终态，重投只能查看原单，不重新冻结或发起上游采购；再次购买需要新键。Paid 返回原服务；Unpaid 返回原待付账单，发起新的 payment attempt 仍须客户明确支付操作。
7. **纳入密钥轮换与保留。** 将新的 encrypted_request 纳入既有 ReencryptSecretsAction 的加密 JSON 字段遍历；轮换前后重试仍命中同一订单。仅增加受保护快照，不把 APP_KEY 或可被字典推测的明文敏感摘要持久化。新列不授权删除旧账单、合并历史重复单、回收 sold 卡密或修改历史余额。
8. **规则同步范围。** 批准后补充独立购买请求幂等规则（新 INV-K5）及章程对应说明；不变更 INV-K1/K2、结算金额、上游成本对账和 C20/C21。迁移仅在临时 SQLite/独立 MySQL 验证，不直接迁移既有业务/隔离验收数据库；部署应用迁移另行安排。

### 获批后的验收

- 同键相同请求在纯钱包、组合、纯网关及零额订单中只生成一个账单、一次冻结/结算、一次用券和一份交付任务；新键可以合法再次购买。
- 并发双进程、响应丢失、报价期间另一请求先提交、同键不同参数、不同用户、终态重投、调价/规则变化/供应商不可用和密钥轮换均覆盖。MySQL 8 证明唯一约束及资金结果，SQLite 顺序测试不能代替。
- 对三个直购表单和配置/报价页面检查键的保留，不修改旧资金断言、不加 skip/ignore；三道默认 Gate 全绿。旧重复订单仅列清单，不自动处理。

## C23 / FIX-005：过期续费的显式恢复单

### 状态：已获人工批准（2026-11-18），实现及隔离验收完成；见 backend-fix005-renewal-recovery.md

C14 已明确“已取消/过期的原账单不因此获得重复扣款授权，其后续重新支付/恢复策略必须显式设计”。C22 只授权新购请求键，不覆盖续费恢复关系、INV-K1 调整或既有数据库迁移。用户已明确批准“C23，按方案实施”。本节允许以下迁移文件与定向规则/流程实现；现有预览/业务数据库迁移和真实上游写调用仍不在本次授权内。

### 已确认的卡点与复现

- `CreateComboInvoiceAction::service()` 按认证到期边界查询 `billing_period_key`，存在就返回，不区分 Expired。传入新的 request_id 也不能绕过该账期。
- `InitiatePaymentAction` 对非 Unpaid 或时间已过期账单明确拒绝付款。`ClassicExpansionTest` 的终态用例严格要求普通续费请求继续返回原 Cancelled 账单，这条断言正确，不能改成自动重开。
- 在临时 storage、SQLite `:memory:`、随机 APP_KEY 和无外网驱动替身中已复现：创建续费单1→过期→使用新 request_id 再续费，仍返回单1 / Expired，支付错误为 `Invoice cannot be paid.`；钱包100.00/冻结0.00，一张账单，零任务、零支付尝试、零财务流水。脚本 `/tmp/reproduce-fix005.py`，日志 `/tmp/backend-fix005-reproduction.log`。没有真实供应商或业务数据库访问。
- 开工 Gate：671 passed / 5515 assertions，PHPStan 0，Pint clean；Specs 0。

### 提请批准的确定方案

1. **保留账期根单，增加两列关系，不转移唯一键。** 新迁移在 invoices 增加：
   - `renewal_root_id BIGINT NULL`，自引用 invoices.id、restrictOnDelete，加索引；只在恢复单上保存最初账期根单 ID。
   - `replaces_invoice_id BIGINT NULL`，自引用 invoices.id、restrictOnDelete，并建立唯一索引；一张过期单最多只有一个直接后继。

   原单继续持有原 `billing_period_key = {instance}:renew:{due_boundary_utc}`；恢复单 `type=renew`、`billing_period_key=NULL`、`purchase_request_id=NULL`。原账期唯一根＋每个前驱唯一后继形成可追溯链，不使用随机账期后缀、覆盖原账单或回收唯一键。既有/非恢复行两列均 NULL，不回填猜测关联。所有恢复单的用户、实例、商品、币种和账期须与根单对应；根单不能是另一张恢复单，链条禁止分叉/循环。

2. **仅显式恢复已实际过期的末端。** 首轮只接受状态已为 Expired 的 renew 账单；Unpaid（包括仅时间超时但 sweeper 尚未完成过期解冻）、Paid、Cancelled、Refunded 均不能进入。链上如已有 Paid 或 paid_at 非空、未决/已付款的上游续费意图、未核对的任务、异常关系或缺失原操作快照，拒绝自动恢复并明确核对原因。原单有 credit_applied 时，须核对该单应有的 freeze/unfreeze 唯一流水，不能以“用户全局 frozen_credit=0”代替逐单核对。旧券使用次数仍按 INV-K4 保留，不返还、不搬到新单。

3. **先展示报价，再由客户确认。** 客户本人账单页提供“重新核价并恢复续费”；使用 CSRF 保护的 POST 报价，再 POST 确认，携带稳定 ULID request_id、短期加密 quote_token、钱包/网关选择、优惠券、明确确认与原因。报价不创建账单/任务，不冻结资金或消耗用券额度。token 默认5分钟（SettingService），绑定本人、根/前驱、当前供应商绑定、认证到期边界、周期/配置、可信上游成本、客户价格、优惠及钱包/网关分配；只在请求体传输，页面 private/no-store。展示新旧金额和新的支付截止时间，客户看到的是本次报价。确认前重新认证同步和读取续费报价；价格、币种、配置、绑定、到期边界、券资格/折扣或钱包分配变化就拒绝本次确认并要求重新核价，不能擅自按另一价格/支付拆分结算。价格和所有金额运算继续使用 Money。

4. **恢复创建仍由既有资金写入者负责。** 在 CreateComboInvoiceAction 增加显式恢复入口；报价/关系辅助 Action 不获得钱包写权限，不改 INV-L2 的写入者集合。先在事务外完成必要的同步/询价，事务内按 `users → invoices（相关根/链/待付单按ID顺序）→ payment_attempts → instances → fulfillment_tasks` 校验并写入：用户/实例归属、链末端资格、原单已解冻、当前绑定和到期边界未变、当前不存在另一张可付单或未决操作，然后按可信报价重新用券、选择本次钱包冻结。根单和原流水不改。纯钱包/零额仍在同一事务内 Paid＋唯一续费任务，提交后投递；其他订单保持 Unpaid 等待客户明确支付。

5. **恢复请求重试与再次过期。** 前驱的唯一后继是持久仲裁：重复点击/丢响应/并发确认不产生第二个后继。将带版本的恢复调用身份（前驱、request_id、确认 token 和支付/用券选择）加密存于 `line_items.recovery.encrypted_request`，沿用已覆盖 encrypted_request 的换钥遍历；`line_items.request_id` 保留既有续费请求定位。相同 request_id/相同调用身份返回原恢复单，已提交单的重放不要求重新报价或未过期 token；同键改参数拒绝。另一请求键针对已被替代的前驱，只定位并展示现有后继，不能据此再扣钱包或修改已存在账单。若后继后来也实际过期，客户须针对新的末端重新核价、确认和请求键，最多再产生一个后继；调度器不能自动替客户做此确认。

6. **结算与旧付款分别处理。** 支付发起、回调 P8 和续费任务创建共同校验恢复链与当前末端，遵守同一用户锁及账单锁顺序，保证一个账期至多一张可结算单。旧 Expired 单始终保持终态；其迟到网关款继续按 P2 验签、去重、credit_in、告警和提交后 ACK，不自动转成恢复单的支付或再次解冻。恢复单在自己的 invoice_id / callback / ledger / task 唯一键下结算，原金额恒等式、CNY 限制和 P1/P6 等规则不变。不新增账单类型、状态、交易类型或 callback outcome。

7. **普通续费与上游防重放。** 没有显式恢复操作时，普通 renew 请求不会凭新键重开终态单；有恢复链时，普通账期查找/调度定位当前末端，指定已存在 request_id 的重放仍返回该请求原单。恢复前认证的到期边界必须仍等于根单：已在上游续费、删除、取消、换绑等情形不为旧边界另收一次费用。执行沿用 create_requested / invoice_created / payment_requested 等持久意图和成本对账；创建/付款响应未决不能通过恢复流程重发。客户付款后若远端又被外部变更，任务仍须预同步并停在核对状态，不保证外部状态永不变化，不自动退款或再次采购。自动恢复仅适用于现有已核实的续费报价/执行契约；长期逾期的计费或起算点无法确认时明确转人工，不推测新的到期日规则。

8. **客户与运营界面。** 客户只能核价/恢复本人账单；服务页和旧单页展示根单、后继、当前待付单及恢复限制，提交成功跳到新单。Filament 财务核查页沿用 finance.view，展示恢复链、付款/解冻/任务证据及不可恢复原因，便于操作员核对。首轮运营入口只核对，不授权操作员代客户使用钱包；客户实际恢复写审计（actor、原因、根/前驱/后继、金额/支付选择），后台仍无任意改状态或绕过成本确认按钮。越权、CSRF、私密快照不得出现在公开页或日志。

9. **批准后的定向规则及实施范围。** 定向澄清 INV-K1：同边界一个唯一根单，显式恢复通过唯一前驱链形成新的付款授权，而非自动重开；补充恢复链的结算限制及章程、guardrails、相关规范说明。INV-W4 的终态冻结、INV-K2 的每单任务唯一键、INV-K4 的用券消耗、C20/C21/C22 均保持。保留原终态和资金断言、所有 Specs；只新增恢复行为测试，不通过改旧期望实现功能。schema 与流程仅在临时 SQLite/离线 MySQL 8 验证；不直接迁移现有预览/业务数据库，不修历史余额、券次数或账单状态，不执行真实供应商续费、付款、暂停/终止。
