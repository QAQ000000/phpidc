# 外部佣金提现实施方案（D03 已批准）

日期：2026-11-18。对应 FIX-021；D03 已批准并实现。本文保留设计依据，验证见 [五项能力实施验收](remaining-capabilities-implementation-2026-11-18.md)。首期采用人工转账凭证闭环，未授权或执行真实打款，未修改既有数据。

## 现状与需确定的范围

当前 `RequestAffiliateWithdrawalAction` 只接受钱包目标，`ProcessAffiliateWithdrawalAction` 的 approved 意味着本地佣金转钱包已完成。Epay 的已验证协议是收款，不提供已经核实的代付/查询/代付回调协议。不能将收款接口当作出款接口，也不能把审批等同于外部转账完成。

推荐首期实现**客户申请→财务冻结→人工执行转账→凭证确认/未付款释放/不确定核对**闭环。系统记录真实已完成的外部付款，不调用未核实的自动代付接口。若业务要求自动代付，先指定供应商和其付款、幂等、查询、回调协议，再实现对应纯适配器；不能用模拟供应商声称实际支付接入完成。

## 推荐业务规则

1. 仅 CNY，金额使用 Money；建议首期 1.00–10000.00 元，每笔手续费由商家承担，申请额等于应向客户支付额。用户提交银行转账或支付宝收款信息，使用独立加密字段保存，不写入审计/通知正文。
2. 沿用 `request_key`（用户 ID + 稳定 ULID）与现有唯一索引；保存不可变的金额、目标、收款方式及加密收款快照。相同请求完全重放返回原单，改变金额/目标/收款信息拒绝。
3. pending 申请沿用待审占用计算；财务批准时再次检查应收、可用佣金和权限，在同一事务将 `affiliate_balance` 转入新增 `affiliate_frozen_balance`，写唯一冻结流水、审批原因和审计。不得改动普通钱包。
4. 审批后的 `reserved` 仅表示资金已冻结；财务开始执行前生成并持久保存唯一 `payout_intent_key`，转为 `processing`，展示固定收款快照和原执行标识。人工在系统外转账，平台不自动调用银行/支付宝。
5. 只有带独立 `finance.external-payout.confirm` 权限的人员核验金额/币种/已完成凭证后才能确认为 `paid`；同事务消耗冻结佣金、追加唯一 `affiliate_payout` 流水和审计。外部交易标识有唯一约束，重复同凭证幂等，凭证冲突或金额不符拒绝。
6. pending 可驳回；reserved 且尚无执行意图可取消并解冻。processing/unknown 不能普通驳回或自动释放；必须以原笔证据确认已支付，或由明确核对操作证明未付款后解冻并终止该单。所有动作记录原因与证据，结果不确定继续冻结，不提供重新出款按钮。
7. 对已经 reserved/processing/unknown 的款，退款追回只能扣可用佣金，不能挪用冻结出款。不足部分继续产生退款应收；后续退回冻结款不会静默清偿应收，仍由独立清偿流程核对。
8. 提现申请、批准、资金移动、执行结果与对应通知事件均在本地业务事务内落库；通知失败不能撤销已完成的财务事实。任何真实验收转账须另外指定账号、额度和授权。

## 增量结构及冻结契约变化

- `users.affiliate_frozen_balance`：`DECIMAL(12,2) UNSIGNED DEFAULT 0`，cast 为 `decimal:2`；注销阻断检查包含该字段。
- `affiliate_withdrawals` 增加加密收款快照、收款方式、唯一执行标识、外部交易标识、执行/确认人员与时间、加密证据；保留原列及钱包旧单状态。具体长度与索引在合并 schema 清单中确定。
- 外部单新增 `reserved/processing/unknown/paid/failed/cancelled` 状态；旧钱包 `pending/approved/rejected` 保持原语义。通过独立 Action 区分钱包审核与外部执行。
- `TransactionType` 定向增加 `affiliate_freeze/affiliate_unfreeze`：分别表示可用佣金与冻结佣金之间的移动；已有 `affiliate_payout` 对外部单表示实际消耗冻结佣金。正金额、方向由类型表达，流水追加式，不重复扣款。
- 新增独立外部提现审核、确认及核对权限；不将既有 `finance.payout` 自动扩成外部付款确认权。客户页面只展示本人脱敏目标及状态，后台查看完整收款信息须独立授权并记录访问审计。
- 原 `AffiliateFunds::pending()` 必须只计算未冻结待审申请，防止已扣出可用余额的 reserved 单再次占用；退款、注销、财务展示统一读取新的余额定义。

## 锁、接口与实现责任

沿用用户主键升序先锁用户，再锁提现单；余额、应收、请求身份和当前状态必须在锁内重验。新的提现/清偿/通知表锁序须一并补入全局锁序，不得在财务事务中调用外部服务。

root 负责外部提现专用 Actions、模型/schema、客户/后台入口、权限、加密字段轮换、财务/应收/注销集成和设计文档；钱包代理修改共享付款回调前通知 root，outbox 代理提供统一事件接口后各模块接入。共享路由、角色清单和全局规范只由 root 整合。

## 验收矩阵

- 同键同参数重放、同键改收款信息拒绝、重复审批/确认/解冻；跨用户/无权限/缺少原因/未确认操作拒绝。
- 同用户并发申请、钱包划转与外部审批竞争、退款与冻结竞争、应收清偿与审批竞争：独立 MySQL 8 验证锁和金额守恒。
- 客户与管理员均不能把 reserved/processing/unknown 当作 paid；未知状态不产生新执行标识，不释放冻结款；仅有确证的未付款可释放一次。
- 真实外部交易标识不能确认到两张单；金额/币种/收款快照必须匹配，原执行证据可审计。
- 冻结后失败/取消精确回滚可用/冻结佣金；普通钱包始终不变；故障注入使单据、余额、流水、审计、outbox 同时回滚。
- 收款隐私在 HTML/日志/异常/通知中符合投影与授权边界，APP_KEY 轮换覆盖新增加密字段。
- 隔离浏览器完成手工凭证流程，使用明确标注的模拟凭证；不执行真实转账，不把模拟验收写成供应商接入通过。
