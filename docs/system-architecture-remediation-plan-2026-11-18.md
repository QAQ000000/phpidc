## 4. W1：修共享调用契约与金额写入

### 4.1 身份邮件异常

保留 `MailDriverInterface` 和现有异常分类，让 `CustomerIdentityAction` 显式处理 `RetryableNotificationException`、`UncertainNotificationException` 及明确的传输失败。分类记录审计和业务结果，HTTP 不因已知邮件故障泄漏 500。

找回密码继续保持防枚举响应；已生成的 token 和 broker 节流遵循现有规则，不用删除 token 或放宽节流来掩盖失败。验证邮件按当前已登录入口提供可理解的失败/待核对结果。发送结果未知不自动重发，不将带 token 的身份邮件直接套入普通业务通知持久化模板。

验收覆盖真实邮件适配器异常分类到 Action、HTTP 和审计的整条链路：明确临时拒绝、明确失败、发送未知、成功及重复请求；不得只 mock Action 自己。

### 4.2 钱包统一容量保护（N05）

统一固定点金额预检，仍只用 `Money`。覆盖普通商品超付、充值、终态迟到款、退款、到期/取消解冻、佣金转钱包及新钱包结清，逐项检查全部调用者。

容量以最终资金状态计算。例如本次支付消耗账单冻结后才增加超付额，应计算完整的净状态；账单解冻与结清解冻仅在三类钱包分量之间移动，不应重复计入新增资金。每列仍须合法且非负，佣金资金保持独立。注销资格、清退查询与财务核查均必须纳入新增结清冻结列。

普通商品超付先校验完整入账方案，再改变 Paid、账本、实例或任务。无法完成时保存已验证原回调及 `wallet_capacity` 原因、持久告警，提交后 ACK；不截断、不部分入账、不因异常使回调证据一起回滚。历史超出新总上限的用户不自动调整余额：阻断新增贷项，允许合法消费、结清冻结/支付及不增加合计的内部释放；不能要求这些腾容量的动作先满足总量上限。每个目标列仍须不溢出。

验收使用隔离 MySQL 覆盖报告中的 `9999999999.99 + 0.01` 普通超付复现、含账单冻结的净额计算、冻结/解冻、退款与回调竞争、重复回调和事务失败。异常处理完成前没有履约；正常收款和账本断言不减弱。

## 5. W2：把资金和一次性交付用户带到合法退出终点

### 5.1 独立钱包结清（N01）

建议新增 `wallet_clearances` 和 `users.wallet_clearance_frozen`。后者使用与钱包相同的金额精度，**不复用用于账单的 `frozen_credit`，也不动佣金冻结**。

请求保存原 `user_id`、场景 `closure_balance / closed_account_receipt`、CNY 金额、稳定请求键、加密收款资料、原笔贷项关联、审批/执行/确认人员及时间、执行标识和加密凭证。

| 动作 | credit | wallet_clearance_frozen | 新增账本方向 |
| --- | --- | --- | --- |
| 批准冻结 | 减少申请额 | 增加申请额 | `wallet_clearance_hold` |
| 确认已付 | 不变 | 减少申请额 | `wallet_clearance_paid` |
| 执行前取消 / 确证未付 | 增加申请额 | 减少申请额 | `wallet_clearance_release` |

各方向采用 `wallet_clearance:{id}:hold/paid/release` 唯一引用；现有 `frozen_after` 继续表示账单冻结，新冻结快照在明确的账本 meta 中记录。不得用任意 adjustment、假商品退款或只改余额实现清退。

状态复用 D03 的业务方式：`pending → reserved → processing → paid`，执行结果未知转 `unknown`。执行意图提交后才能线下转账；未知状态不能普通取消、自动解冻或重开付款。仅执行前取消或已证明未付可释放；真实已付款不能靠本地“冲正”恢复余额。

本人申请需要密码及明确确认；财务审批重新验证余额、应收和未决资金问题，执行与确认按 D03 的职责隔离方式授权。`wallet_capacity / closed_account` 来源案件本身不阻断清退已确认可用的钱包余额，否则无法腾容量或清退迟到款；未入账收款不能使用，未清应收、未知出款等其他资金阻断保持。注销必须等待结清结束，不能提交一笔 pending 申请后马上绕过余额阻断。

匿名身份迟到款由专门财务权限按原 `user_id`、原笔交易和受款权利证据审核，不凭已释放邮箱/手机号领款，不复活账号。先核实原笔完整入账，再结清真实旧钱包余额；未入钱包的资金不能直接在清退中扣钱包。首期每笔匿名清退只关联一个来源案件及原贷项，一源可分多笔支付，同一已付金额不能重复消解多个案件。设该来源已确认入旧钱包、需清退的本金为 L，累计已付为 P，reserved/processing/unknown 的当前有效冻结为 H：必须 `P+H≤L`，新批准额 `≤min(credit,L−P−H)`；pending 不占冻结，批准时重验。结案须 `P=L 且 H=0`，全部金额计算仍只用 `Money`。

新增共享 `external_payout_receipts`：沿用已确定的渠道/交易号规范化口径，外部凭证键唯一，对应业务 kind/id 唯一，记录金额/CNY。钱包结清和现有佣金外付确认在事务内原子占用，避免同一转账分别确认两笔支出。历史已付佣金只补登记，不重写账本；冲突必须形成核对清单，不能取第一条覆盖。已付凭证不因本地取消或重试释放。

### 5.2 一次性交付权益归档（N02）

新增 `instance_entitlement_archives`，保存实例、原用户、稳定请求键、交付证据指纹、本人确认和归档时间。通过显式能力接口识别一次性交付，不按驱动字符串分支，也不能只判断 `billing_cycle=onetime`。

首期允许已确认完成的本地卡密、本地 Sub2API 卡池及远程固定码交付；要求付款/交付证据完整、无未决任务或远端结果、没有持续资源费用。外部远端权利仍持续维护的产品不能冒充一次性交付。

归档不改实例 Active、已售卡、原付款及原交付，不回收或再次出售卡密，不撤销外部兑换权利。注销资格只对匹配当前交付证据的有效归档放行；本人在注销前获知应保存交付资料，原历史按既定受限权限保留。

## 6. W3：让历史异常和热切换可以结束

### 6.1 类型化异常处置（N03）

建议新增 `reconciliation_cases` 和 `reconciliation_entries`。案件仅支持 `binding_orphan / payment_attention` 两类，关联原 binding 或 callback、原用户和事实指纹；来源唯一。追加处置记录保存请求键、预期版本、规定结论、加密证据、实际结果引用、操作人及原因。案件头是追加记录的投影，不是可任意改状态的业务事实。

| 来源 | 首期允许的结案条件 | 不能作为结案证据 |
| --- | --- | --- |
| `kept_orphan` | 认证查询原绑定确认 Deleted；或核实接收主体、目标资源及责任接受的移交证据 | 删除申请已受理、管理员已看过、只把原 binding 改值 |
| `wallet_capacity` | 腾出容量后，按原回调和当前账单状态重新计算并实际完成唯一入账/结算 | 只删告警、只增加一条处理说明、重复记本金 |
| `closed_account` | 该笔迟到款及对应旧钱包义务已按 N01 实际清退，金额与凭证匹配 | 仅把钱放入已注销钱包、向同邮箱新账号付款 |

容量异常的补记通过专门 `ReconcilePaymentCallbackAction`，引用原 callback ID 和已验签事实，不删除回调或重发 HTTP 来绕过重复检测。仍可支付的原账单按原组合支付规则原子结算；已 Paid/Expired/Cancelled 等状态按既定完整迟到款/超付规则处理，不复开账单。与账本、任务、outbox、案件结论同事务提交，同回调只能补记一次。原账号已匿名时不交付、不复活；补记到旧钱包后转为等待清退，不能直接结案。部分清退、冻结、processing 或 unknown 均不等于完成。

首期不另造“未入钱包收款直接外退”的执行状态机；未满足上述真实处置条件的案件保持开放。将来若需要该能力，应独立决定原路退回、执行意图、凭证和未入账资金清偿规则，不能临时套用钱包结清。

历史 attention 和 orphan 建立一对一案件，默认待核对，不自动认定已经处理。资格判断必须同时覆盖尚未建案的来源，避免回填未完成出现放行窗口。原审计、callback 与 binding 历史不改删；后续证据推翻结论时追加重新打开记录，已匿名账号不复活。

### 6.2 热切换映射核准（N04）

新增 `instance_mapping_reviews` 保存不可覆盖的核准快照，提供“检查映射 → 核准应用”两步后台入口，单独授权并要求理由。

1. 在事务外认证读取当前目标主机、account/pid、实际配置、目标目录、周期、CNY 和成本；仅查询，不发远端变更。
2. 使用匹配目标 account/pid 的本地商品，验证全部实际选项的明确映射，不能直接复制旧商品选项 ID。保存绑定、账户与目录指纹。
3. 按统一锁序重新校验用户、实例绑定、账户、目录、账单与任务；材料过期、目录变化、再次换绑或出现未决业务均拒绝应用并重新检查。
4. 同事务保存核准记录，重建 `options / upstream_configoption / binding_pay_type` 等未来操作依据，关联核准 ID 后解除 `mapping_requires_review`。必要时更新实例未来使用的 `product_id`，历史账单和原购买快照不重写。

默认保留已核实的客户续费价格和到期基线，目标成本与售价分别保存。若现有锁价与目标选项不能形成可验证基线，继续阻断升级/降价，先完成明确价格确认；不能填一个金额或只改 bool 过关。原有续费、退款及终止规则不因映射核准获得绕过权限。

## 7. W4：控制调度、查询和故障发现成本

### 7.1 调度公平性（ARCH-08）

推荐分钟调度只将七类本地批处理投递到独立 `maintenance` 队列，各类具有去重/互斥；业务动作仍在现有 Action。保留 `withoutOverlapping`、`onOneServer` 与原上游保护，不能把 scheduler 的互斥误当作异步 Job 的互斥。

初始参数建议：2 个本地维护 worker，每个 Job 最多处理 100 个候选、软预算 5 秒、超时 25 秒，维护连接行锁等待上限 2 秒；采用单次队列尝试，由下轮到期条件重新补扫，保留业务自身退避。现有 `retry_after=240s` 与 worker 停止余量须一起核验，不设成小于 Job 超时。单类排队/运行去重 TTL 建议 180 秒、执行互斥 30 秒。这些是待隔离测量的起点，不是已测容量。主调度保持 55 秒，只负责快速投递。

对佣金计提和成熟分别保留独立预算，避免第一段耗尽第二段；候选建议每批 50 条最早到期 + 50 条轮转 ID，各子类独立游标，走完回绕，确保旧 ID 后来到期不会永久漏掉。单条锁超时/坏证据不能让整批从最前方永久重试：记录原项，按现有幂等规则退避，其他符合条件项仍有处理机会。游标丢失可从原持久状态重建。失效任务租约和 unknown 保护不能因新队列被重置。通知事件的接收者展开也须分批且可恢复，不能静默截断扇出。

不增加经典上游/真实履约 worker 并发。目录批处理仅补扫/派发，真实网络任务仍在原执行边界；不能只用 `runInBackground` 绕开 systemd oneshot 的进程生命周期。

### 7.2 应收查询与资金锁（ARCH-09，N06）

先做低成本整理：推广页只计算一次投影；根记录及清偿历史分页；使用 keyset/chunk 批量验证，避免一次把所有 root、settlement、reversal、ledger、commission 放入内存。展示总额与分页明细口径必须一致，不能把一页的合计伪装成总额。

资金准入保留现有“坏证据也阻断”语义，不换成 `SUM(remaining)`：

1. 新增单调递增的 `receivable_revision` 及持久 `receivable_reconciliation_required` 标志；退款产生/变更应收、清偿、冲正以及影响有效性的所有合法写入者，必须在同一事务、同一相关用户锁内递增版本。参与用户先按 ID 排序锁定。
2. 资金动作先在锁外、同一数据库连接的一致性快照内读取版本并严格校验完整证据，结束快照后再进入资金事务，拿用户锁核对版本及失效标志；变化则退出事务重算，不能持锁重扫全部历史。
3. 扫描使用有界内存；核验未完成、超预算、解密失败或版本连续冲突返回“待核对”，不能返回无应收。长历史的核对任务独立执行，只有与原操作、原用户及仍相同证据版本匹配的完整结果可以用于该操作，不提供手填余额的放行入口。
4. 初始前台预检预算建议 2 秒，版本冲突最多自动重算 2 次；超出转待核对。长历史路径必须在容量验收中证明可完成，不能把合法大账户永久挡在超预算状态。

长历史任务采用独立 `receivable-check` 队列，初始 1 个 worker、软预算 90 秒、超时 120 秒，连接 `retry_after` 与停止余量须大于此超时，不占用 maintenance 或上游 worker。任务在一致性快照内完成全部严格校验，服务端将结果暂存到受限 Redis，TTL 建议 10 分钟，绑定 `user_id + 动作种类 + 稳定请求键 + 规范化参数HMAC + revision + 校验算法版本 + 证据摘要`。前端只能查询状态并继续同一原操作，不能提交“已检查”作为凭据；资金 Action 在锁前读取服务端结果，在锁内重新核验 revision/失效标志、原参数和业务幂等，再检查余额与当前状态。Redis 丢失只导致重新核验，不能成为资金事实丢失。

超前台预算后转上述长任务，不能每次重新从零跑同样 2 秒。验收必须证明 10000 根/100000 证据能够在长任务预算内产出完整结果，并完成原资金操作；不通过则继续优化查询/索引和流式校验，不宣称此容量已支持。超长任务失败保留明确原因并通知运营，不把失败结果当成无应收。

该方案缩短资金锁，不承诺每次校验全历史为常数成本。版本可信的前提是所有合法证据写入者纳入同一规则；任意带外改库不在此一致性保证内，人工修复/导入必须停相关写入并递增版本、重新严格校验。独立定期全量严格巡检发现坏证据后，在用户锁内设置失效标志并递增版本，使旧预检结果失效；只有完整复核通过且授权核准后才可清除标志并再次递增版本。不能声称扫描间隙能实时发现任意原始 SQL 损坏。Redis 结果只用于原请求，不允许当成跨操作的通用余额缓存；若未来改为持久余额投影、缓存跨操作放行或降低损坏检测及时性，须另行决议，不能作为本次的隐式优化。

### 7.3 故障发现与处置（ARCH-07）

首批持久运营事件覆盖：履约最终失败、恢复耗尽、供应商回滚失败、原始应收产生、付款待核对及通知 uncertain。正常业务事件与对应状态同事务；最终失败、供应商回滚失败等事实若原事务将回滚，须在其回滚后用独立短事务持久化，并保留结构化 journal 兜底，不能让告警一起回滚，也不能让记录告警失败覆盖原故障。全部使用唯一事件键，明确关联原任务/收款/应收，避免每次补扫产生新告警。

巡检需独立于 outbox：建议新增只读 `app:operations-check --json`，每类最多输出 20 个样例 ID，由独立 systemd timer 或外部 agent 每 60 秒执行、10 秒超时，退出码/结构化结果交给独立监控出口。数据库/Redis 不可达、巡检超时或自身心跳过期也必须告警，不能依赖同一个可能失效的通知通道报告自身失效。应收严格巡检是另一个可写失效标志的受限动作，不能混进这个只读命令。运营告警必须配置至少一位实际接收者和明确值班责任。

| 指标 | 推荐初始阈值 | 处置 |
| --- | --- | --- |
| outbox due-pending 最老年龄 | >120 秒告警，>300 秒升级 | 查维护队列、投递 worker 与最近成功时间 |
| notification uncertain | 新增即进入人工核对，15 分钟未认领升级 | 核对原发送结果，不自动重发 |
| 无运营接收者的关键事件 | 大于 0 即配置告警 | 补齐责任人并核对原事件接收者展开 |
| 分钟维护任务最近完成时间 | >150 秒告警，>180 秒升级；非分钟任务按各自周期设置 | 查 Job 锁、队列和执行时长 |
| 最终履约失败 / 回滚失败 | 新增即告警 | 关联原任务/上游操作，按原动作核对 |

阈值为初始建议，需以隔离积压测试及实际值班能力校准；监控降噪不能删除业务事件或把 uncertain 改成成功。

## 9. 验收以旅程为单位

| 旅程 | 必须成立的结果 |
| --- | --- |
| 旧库升级 → 老推广页 → 现有商品付款 | 无缺表；Paid/账本/任务/outbox 原子一致；部署检查不以 GET 200 代替 |
| SMTP 拒绝 / 失联 → 找回密码 / 验证邮箱 | HTTP 和审计可控；防枚举、节流及未知结果保护保持 |
| 商品超付容量不足 → 告警 → 钱包结清 → 原回调补记 | 原回调留存、无提前履约、一次补记、真实结果后结案 |
| 钱包剩余 0.01 → 申请 → 人工付款 → 注销 | 钱包和结清冻结为零，有唯一外付凭证，无调账假退款 |
| 已注销原身份 → 迟到款 → 清退 | 只使用原身份；同邮箱新用户不能认领；未知出款不重试 |
| 卡密购买 → 交付 → 本人归档 → 注销 | 已售卡不回池，实例/历史交付保留，未决远端结果仍阻断 |
| 热切换 → 原资源核对 → 映射核准 → 再升级 / 续费 | 核准基于当前真实绑定，原售价不被暗改；旧资源有实际处置 |
| 佣金外付与钱包结清并发确认同凭证 | 数据库唯一约束使仅一笔成功，不双重消耗冻结 |
| 资金准入预检 → 同时清偿 / 冲正 / 退款 | 证据版本变化拒绝旧结果，坏证据仍阻断，资金锁不扫全历史 |
| 批处理积压 / 单条锁等待 → 后置 outbox 补扫 | 各维护类型均有进度，调度预算不饥饿，重复执行不重复业务 |
| worker/Redis 中断 → 恢复 | 事务 outbox 和任务可补扫，unknown 不盲重发，未丢业务事实 |
| 数据库 / 文件 / 密钥恢复 → 部署检查 | 同检查点可恢复、密文可解，权限与队列均实际验证 |

隔离容量验收至少包含一个用户 10000 笔应收根、100000 条清偿/冲正历史，以及多个用户批处理积压；数据全部合成，不能复制明文真实凭证。记录硬件、数据量、P95/P99、峰值内存、SQL 数和资金锁持有时间。初始目标：普通分页 P95 ≤500ms、资金锁 P95 ≤100ms、每种到期维护类型在 120 秒内至少完成一轮有界处理；目标以指定 MySQL 8/Redis 隔离环境实测确认，未达到不能标为已通过。测试同时覆盖前 100 条毒数据/锁忙、旧 ID 后来到期、游标丢失、批中断，以及停应用调度/worker 且所有通知驱动故障时独立监控仍能发现问题。

## 10. 实施与发布门禁

1. **共享设计门禁**：N01–N06 明确，schema/权限/锁序/写入者清单完成，独立架构审查不存在相互矛盾的资金口径。
2. **代码门禁**：新增有意义的跨模块回归及 MySQL 并发测试；保留旧严格断言、旧迁移与 Specs。完整 Pest、PHPStan、Pint 通过；1068/9033 是既有历史基线，不是本方案已跑的结果。
3. **隔离运行门禁**：完整升级、旅程、积压、公平性、容量及同检查点恢复完成；外部通知/支付/供应商使用隔离替身，禁止误调用真实通道。
4. **实际环境发布**：明确目标库和操作范围 → 维护边界及外部回调暂存/重试策略 → 停本项目 timer 并等待调度退出 → 排空/停精确归属本项目的 worker 和写入进程 → 同检查点备份数据库、私有文件、密钥材料及代码/依赖 → 迁移/回填 → 配置和权限 → 以实际 `www` 运行身份做部署检查 → 先启动 worker/独立巡检，再启用调度 → 业务验收 → 开放流量。不能停止共享数据库/Redis，不能只关菜单保持旧代码写库。
5. **实际业务验收**：优先使用已有测试产品，支付/通知/供应商变更逐项记录动作和额度范围；历史某次真实购买额度不能自动扩展为本次升级/退款/清退额度。测试账号与管理员权限分开准备。
6. **失败恢复**：有真实新账务后不执行盲目 migrate rollback，也不能直接 git 回旧代码：旧 enum 可能无法读取新账本方向。暂停相关写入，保留外部交易事实，优先前向修复；必须恢复备份时，对备份后回调/出款/上游动作先形成对账清单，不能丢弃这些真实结果。
