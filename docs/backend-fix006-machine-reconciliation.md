# FIX-006：机器命令未决后的人工核对与恢复

日期：2026-11-18（Asia/Shanghai）。范围仅限[问题清单 FIX-006](backend-review-remediation-2026-11-18.md#fix-006机器命令未决后缺少人工核对恢复入口)。保留此前未提交改动及用户上游 API 总册，不修改 Specs、冻结接口、DTO、枚举、表结构或规范性业务不变量。

## 操作流程

1. 后台“上游服务”进入“机器命令核对”；`upstream.view` 只能查看原请求、原/现绑定及最近30条脱敏审计，GET 不访问供应商。`upstream.lifecycle` 才能发起查询和提交结论；Action 在网络返回后锁定重新读取的操作员行，复验权限。客户和库存角色没有恢复权限。
2. 原请求提交至少五分钟后才可核对，并与客户机器操作共用实例互斥锁。查询只调用既有认证 `/host/header` 和广告了电源能力时的 `func=status`，没有重发机器变更、自动重装、重启或救援。供应商返回主机 ID 时必须匹配请求资源；异常快照记为不可用，不能据此释放。
3. 查询记下原因、操作员、时间、实例及公开绑定和脱敏现状审计，产生默认五分钟的加密凭证；期限由 SettingService 的 `machine.review_token_minutes` 读取。凭证绑定原请求全量意图和用户/驱动/账户/主机/下游令牌/地址；私密字段不进入页面、URL或审计。确认页展示有效期，凭证不进入错误闪存。查询和确认均为带 CSRF 的 POST。
4. 默认“保持未决”只追加核对记录，后续命令继续被阻止。供应商不可用时也可以记录调查，但不能释放。
5. “允许新请求”必须填写供应商任务面板或工单来源、任务/工单编号、至少20字证据摘要、重新输入上游主机 ID、任务终结时间及原因；单独确认原任务已终结且没有排队/运行中的相关命令。结论只能是已完成、失败且终结、确认未执行且不再排队。任务终结时间不得早于本地请求或在未来。运营不能仅点击一个无证据的“清除”按钮。
6. 确认时重新查询现状，在事务内按 users（客户和操作员按 ID 排序）→ instances → fulfillment_tasks 锁序核验原意图与绑定、当前权限、Active 服务、没有终止申请及未决任务。认定开机/关机/硬关机“完成”还要求当前电源与目标一致；其他操作必须由操作员独立核实任务证据，不能从电源推断已完成。HTTP 始终在事务外，驱动不落业务数据（INV-L1/L3/L4）。
7. 原 `requested/unknown` 不改成 accepted/completed；JSON 仅增加同事务提交的核对审计指针。新请求放行要求指针确有本实例、原请求、released=true 的审计和匹配的加密绑定。核对结论标记 `verification=operator_attestation`，表示人工核实，不冒充机器自动证明原命令成功。账单、钱包、生命周期和客体凭据均不随核对变化。
8. 确认表单使用稳定 resolution ULID；同键同参数重放返回原提交结果，即使凭证过期、换钥或之后已有新命令；同键改参数拒绝。数据库锁和锁内当前读负责两个进程的最终判定，缓存锁只是减少冲突。原机器请求 ULID 的请求审计仍永久阻止其重放，只能以新 ULID 发起另一次操作。

## 历史记录、热切换与迟到结果

- 新机器意图增加提交时间、重装的非秘密选择参数及 encrypted_binding；不保存救援密码、VNC响应或原始表单。原请求审计记录同样脱敏。encrypted_binding 进入已有维护模式换钥流程，JSON中的业务参数和原请求身份不变。
- 旧记录仅有 request_id/command/status 时，必须存在原请求审计，且请求之后没有热切换审计；还需操作员明确独立核对历史主机归属。不能根据当前主机电源猜测旧绑定。无法确认的记录继续阻塞，不批量补写或清理历史记录。
- 热切换同事务把旧意图及原绑定/原结果、原因、操作者和目标绑定记入 `instance.machine.archived`，清除新绑定中的旧意图及旧面板能力。`requires_supplier_review` 明确旧供应商是否仍需调查，原状态及已有人工核对指针在归档前快照中保留。热切换既有财务核查、绑定历史和回调任务继续生效，不向旧资源重发机器命令。
- 原命令在 header 后准备 POST 时复验绑定（含地址）和核对指针，已恢复或换绑时拦截；结果回来时仍须原 requested、同请求、同绑定且没有核对指针，才允许应用。迟到结果可留审计，但不能覆盖人工结论或新机器/新命令。
- 原请求缺失审计、绑定不符、服务不可用、未决履约任务、凭证过期或确认期间发生变化均保留阻塞并返回可处理的表单错误。确认错误跳回可 GET 的后台核对页，避免刷新 POST 查询地址造成405。

## 协议证据与实际限制

参考成品 `app/home/controller/ProvisionController.php`、`app/common/logic/DcimCloud.php` 与既有驱动协议证明：`/host/header` 是资源快照；`func=status` 是当前电源；命令返回200仅表示受理。没有已核实的、关联本地 request ULID 的上游任务完成查询协议。因此本轮不新增或猜测 supplier job/status 端点，也不实现自动判定原重装/重启/救援完成。

操作员须核对供应商原任务的身份、结果和排队情况，证据摘要不能包含密码、令牌或控制台地址。系统能验证必填字段、绑定和可查询现状，无法验证工单叙述的真实性；没有任务证据时必须保留未决。授权操作员的人工判断是本流程的必要信任边界。

五分钟保护期覆盖正常HTTP认证/重认证、header和命令的超时预算，共享锁及发送前/返回后的复验降低竞态；它们不能实现本站与供应商之间的分布式原子提交。线程若在发送前最后复验之后被任意长时间暂停，或供应商命令仍在延迟排队，仍需先人工确认旧请求已停止且上游队列空闲；不能把本轮测试宣称为消除了该跨系统窗口。

没有发起真实供应商机器变更、终止、付款或人工恢复写入；没有迁移或重置现有预览/业务数据库，没有启动生命周期调度。真实任务完成和供应商排队策略仍未联调。
