## 2. 共用页面规范

- 桌面对象条以一行紧凑布局为目标，约 56px 起；长名称和手机端允许换行，不固定高度裁切内容。对象页不再重复一套大标题卡。
- 全局菜单全部左置；页签只切换当前对象的资料或记录。右侧操作卡只放当前对象动作，不成为第二套模块导航。
- 常规解释收进字段帮助或操作弹窗；真实未决状态、停用／注销状态和阻断原因仍明确可见。图标提示须能键盘聚焦及在手机点击，不能只有鼠标悬停。
- 返回直接来源、列表筛选、页码和当前页签采用服务端白名单重建。无递归历史栈、无任意 `return_url`；来源不授予目标权限。
- 每个跨对象链接只给一个明确主入口，例如“客户 #8”“账单详情”“实例工作台”，不同时摆放多个含义接近的详情按钮。

## 3. 客户详情：当前页签决定查询

固定路径 `/admin/customers/{id}`，缺省 `?tab=overview`。页签均为普通链接，可刷新、分享、前进和后退，无 JavaScript 也能切换。

| 页签／URL 值 | 必须先满足的查看权限 | 当前页签读取范围 |
| --- | --- | --- |
| 概览 `overview` | `customers.view` | 普通资料、账户／实名状态；有 `finance.view` 才选择三个钱包字段；有 `upstream.view` 才查询本地有效服务数 |
| 服务 `services` | `customers.view` + `upstream.view` | 当前客户服务分页，保留连接名称与实例工作台直达 |
| 账单 `invoices` | `customers.view` + `finance.view` | 当前客户账单分页 |
| 流水 `ledger` | `customers.view` + `finance.view` | 当前客户资金流水分页，方向仍由原流水类型表达 |
| 工单 `tickets` | `customers.view` + `support.view` | 当前客户工单分页与原工单直达 |
| 实名 `identity` | `customers.view` | 现有实名状态和脱敏历史；无原件读取或人工通过／驳回 |
| 通知 `notifications` | `customers.view` + `notification.view` | 当前客户通知元数据分页，无正文或收件凭据扩展 |
| 审计 `audit` | `customers.view` + `audit.view` | `subject_type = User` 且 `subject_id = 当前客户` 的原脱敏审计分页 |

每次先验证页签值和权限，再查询该对象及所需数据。已知但无权访问的页签返回 403；未知值、数组等无效输入返回 422，不回退到全量查询。缺省概览始终可供 `customers.view` 使用。页签不为装饰性计数逐一执行全部表的 `COUNT`；首版可不显示数字，已有获授权摘要可复用。

概览只保留一份资料与紧凑指标，不预先查询七张明细表。非概览页签读取必要对象身份，不附带无关钱包或服务聚合。每个明细仍限定当前 `user_id`、显式列选择和每页 10 条；“前往全部记录”携带已有 `user_id` 过滤，不扩大查询范围。

编辑资料、重置链接、停用／恢复、钱包加扣款继续使用 C2／C3 原权限、目标保护和 Action；页签重排不扩大可操作对象。首屏保留高频操作，其他动作可收入明确的“更多操作”。验证失败恢复原页签及对应弹窗，只恢复原本允许回填的输入；秘密和收款凭证继续清空。

分页 URL 只携带当前页签、对应分页键和来源。跨对象返回包含当前页签及页码；既有 `from.section` 通过固定映射恢复相应页签。站内原锚点链接统一补充对应 `tab`，对应面板保留旧区块 ID。纯 URL 片段不会传到服务端，不将其当作服务端路由参数。

## 4. 实例详情：核心事实与操作同屏

主入口统一为 `/admin/instances/{id}`。桌面约左侧 2/3、右侧 1/3：左侧紧凑展示状态、主机名、IP、客户／商品、计费周期、续费金额和到期时间；右侧展示按权限开放的操作。手机端对象条后先显示核心状态和动作，再排列详细事实，不要求横向滚动整页。

操作卡复用既有能力：同步上游事实、读取机器管理菜单、暂停／恢复／终止、显式换绑、映射核准、未决命令核对。生命周期和换绑表单移入当前工作台，复用原 Action、权限、审计与验证，不再要求先去“经典简要详情”。确认弹窗保留真实风险与提交前复核。

详情 GET 只读本地数据，不调用上游、不解密交付凭据。机器菜单继续由管理员**显式 POST**读取；只有原协议实际返回支持的命令才可展示为可执行项，不能先绘制电源／重装／VNC 假按钮。执行、未决复核、VNC 签名和实际管理员身份继续走原协议，无自动刷新、盲目重发或代客登录。

关联账单、任务、工单可使用对象页签按需查询，各自先检查 `finance.view`、`tasks.view`、`support.view`。失败任务重试保持原 Paid、归属、状态和认领校验。没有对应权限时不加载记录、不显示数量。

旧 `/admin/upstream-instances?instance={id}` GET 继续可用，按有效 ID、原权限和来源白名单转到主工作台，并将旧生命周期／换绑来源映射至固定操作位置；未选实例的列表保持原入口。旧 POST、机器、同步、映射和核对路径保留，不用通用 301／302 改写 POST；原无来源表单的默认成功／失败目标继续兼容。

不新增到期日、续费价或归属编辑；上游同步仍按现有事实应用协议更新，不能借 UI 合并制造独立本地覆盖字段。

## 5. 账单详情：金额事实与主操作并列

保留 `/admin/finance/invoice` 的现有定位参数和 `finance.view`。首屏左侧展示客户／账单状态、金额、原支付计划和实际收款来源；右侧按原权限、账单类型及状态展示登记线下款、全额退款或不可操作原因。历史明细、支付尝试／回调、流水和履约任务放入对象页签；任务仍需独立 `tasks.view`。

“原支付计划”继续表达 `总额 = 钱包分配 + 网关应付`，优惠已计入总额。“实际收款来源”分别展示已记录的钱包消耗、网关事实或线下收款；无证据写“未记录”，不能将计划网关额自动当成实收。线下收款不伪造回调、不改写原分配；金额只展示已有定点字符串，不重算历史账单。

凭证 GET 仍仅显示脱敏摘要；查看完整凭证保留受审计 POST、关闭清空和权限核对。原财务幂等、冻结、共享凭证唯一性、全额退款条件和失败回填全部保留。不新增改价、合并、部分退款、人工建单或标记任意金额已付。

应用实施时运行相关 Feature 回归及项目要求的 Pest／PHPStan／Pint 门禁；不得以删除用例、放宽权限或忽略状态来达成新布局。本设计文档本身只作源码与链接核对，不执行迁移、不向预览赋权、不进行真实支付、调账、供应商动作或外部通知。
