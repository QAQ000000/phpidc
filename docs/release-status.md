## 应收容量与竞争证据

`python3 scripts/verify-receivable-capacity-mysql.py` 在离线 MySQL 8.0.35 与 Redis 7、8 逻辑 CPU/约 7.76 GiB 内存的同宿主合成环境验收：一个用户 10000 笔应收根、60000 笔清偿、40000 笔冲正及 100000 条对应流水。MySQL 会话默认 READ COMMITTED，核验明确使用 REPEATABLE READ 快照。八次完整核验 56.79–66.78 秒，样本 P95/P99 为 66.78 秒，均小于 90 秒长任务预算；每次 1304 SQL，PHP 分配内存峰值 48.5 MiB。八个真实资金事务的用户锁测量最高 77.13 ms，小样本 P95/P99 同为最高值，不能外推生产 SLA。

通过真实 `RequestAffiliateWithdrawalAction` / `ProcessAffiliateWithdrawalAction` 完成佣金转钱包，唯一 payout 流水只生成一次。另一个独立 PHP 进程在原资金请求取得用户锁前，真实执行清偿冲正，将版本 1 改为 2；原请求锁内拒绝旧结果并重新排队，没有创建提现。完整重核发现 1.00 应收；真实登记外部清偿将版本改为 3，再用原 ULID 核验并批准成功，最终钱包 19.00、佣金 98.00，两次合法批准只有两笔唯一 payout。

同一夹具上，实际 `FinanceReceivables::getViewData` 分页数据层测量 20 次、每页 20 行，P95 136.05 ms、P99 145.74 ms，共 220 SQL；**不含 HTTP、Filament 渲染或资源加载**。该只读探针在同一隔离实例存活期间另行执行。容器无网络/宿主端口，所有付款、供应商与发送通道均替身，最终容器已删除。生产负载、冷网络和部署账户仍须另验。

## 部署与恢复入口

先读 [部署手册](deployment.md) 和 [维护与独立巡检](maintenance-and-operations-2026-11-18.md)。本批新增两个 maintenance worker、一个 receivable-check 长核验 worker、两个独立检查 timer；模板尚须按目标环境安装验证，不能只启 scheduler 而遗漏消费者。

业务事件和投递、运营事实 outbox 均已持久化。恢复从原任务/事件/游标推进；发送意图、外付 intent、unknown/uncertain 和备份后外部结果先对账，不执行整队列盲重放。数据库、私有文件、APP_KEY、封印与代码/依赖来自同一检查点；换钥覆盖外付、钱包结清、案件和两表通知密文，完整清单见部署手册。

当前支持的退出与异常终点依赖实际结果：未结资金/业务继续阻断注销；无运营接收者的事件保持可见 awaiting；证据不完整、核验超时或版本漂移不会视为无应收；历史无端点证据的绑定不会由当前地址猜测补齐。
