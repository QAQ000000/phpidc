## 金额及失败路径

- 容量计算使用进入事务时的完整锁定快照，检查完整最终 `credit + frozen_credit + wallet_clearance_frozen`，上限 `9999999999.99`；佣金资金保持独立。
- 普通商品回调消费原账单冻结后才增加超付额，因此按完整净结果判断；充值按完整实收一次预检，不能分成两次局部检查。
- 历史合计超限不自动改账；合法消费、冻结、支付和解冻允许合计不增加，每个目标列仍须可存储。纯钱包若中间冻结列将溢出，返回受控核对错误，不改变原 freeze/settle 流水语义。
- 到期解冻目标列溢出时，保留原余额和 Unpaid，追加一次 `invoice.expiry.wallet_capacity` 审计并继续其他账单；终止取消的对应解冻返回受控失败。
- 退款、佣金转钱包容量失败完整回滚；已成功操作的幂等重放在当前容量检查之前返回，不能因余额后来变化重复执行。
- 快照缺任一必要列直接报错，不能把漏选字段或漏迁移当成零。新增 `000008` 必须与当前代码一起部署。

## 数据库和运行验收

离线 MySQL 8.0.35 使用专用 Docker 容器、`--network none`、Unix socket 与独立数据库，不接入业务数据库。第一批增量迁移为既有 `000004`–`000007` 及新增 `000008`。

已实测的金额结果：

1. 钱包 `9999999999.99`、普通账单 `10.00`、实收 `10.01`，相同回调连续两次 ACK：仅一条回调/attention，账单 Unpaid，无账本或履约任务，没有 SQL 1264。
2. 先消费账单冻结 `1.00` 再记超付 `0.50`，完整净额允许，余额 `9999999999.49`、账单冻结为零。
3. 钱包已满、冻结 `1.00` 的到期解冻保留原事实；后续普通到期账单仍可处理。
4. 两个独立 PHP 事务争用剩余 `0.01` 容量：一笔贷项成功，另一笔保留 capacity attention，无字段溢出或余额丢失。

升级演练还覆盖旧业务表/旧行投影哈希保留、MySQL 部分 DDL 成功但迁移未记账时的失败、盲重跑拒绝、同检查点恢复重演、全新安装及本地商品 Paid→账本→任务→持久事件→交付。最终运行状态、证据路径和原预览管理员阻断以[升级专项验收](system-architecture-batch1-upgrade-2026-11-18.md)为准。
