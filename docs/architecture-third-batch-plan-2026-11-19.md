## 核查结果（实施前）

- 应收扫描已按 100 根/500 条证据批量读取，无逐根 N+1；现有索引已覆盖主要查询，不能靠重复建索引消除增长成本。
- 每个新请求仍扫描全部退款应收根、清偿、冲正及原账本。同一原请求仅复用后台完成结果，前台完整扫描结果尚未按该规则保存。
- 实施前的 W4 契约要求新请求完整核验，测试包含“不提升 revision 的直接 SQL 破坏账本，下一新请求发现”。跨请求复用必须明确修改这项检测时效，不能当成无语义变化的性能修补。
- 两条历史表外键仍为 CASCADE；当前无商品/实例物理删除入口，并有其他 RESTRICT 保护。本次属于留存边界加固，不是已证实可利用的数据丢失漏洞。
- 两个已认领任务结果提交点按普通 User 查询，历史软删原用户会使提交失败；扩大历史读取必须同时禁止停用账户的新认领。

## B3-01：有限期复用完整核验结论（推荐）

复用现有 `receivables.cache_store`，不新增应收余额列、汇总表或根投影框架。

1. 仅将原完整扫描的有效结论保存为加密临时证明；绑定 user_id、receivable_revision、算法版本、APP_KEY、持久失效标志、摘要、原扫描开始时刻与到期时刻。仅包含证据结论与总计，不含请求金额、支付账户或密码。
2. 有效期不超过 **600 秒**，从原完整扫描开始时刻计算；命中不续期。合法写入提升 revision 后旧证明立即失效；密钥/算法变化、缓存丢失、解密失败或不完整证明均重新扫描。
3. 跨不同请求的复用只用于无需捕获特定应收根、且不允许失效标志的普通准入，如提现、钱包清退和注销。每个操作仍自行鉴权、验密和校验意图；资金事务锁内继续核对用户、revision、算法及失效标志。
4. 清偿/冲正、跨账户纠正、应收明细页面等带 capture_ids 的操作继续完整扫描；不使用旧结论代替原根证据。人工复核解除标志和独立审计也继续完整扫描。后台原请求的已完成全量结果仍按现行准入规则使用。
5. 前台完成的全量核验结果也保存到现有“原用户/动作/请求/意图”状态，保持同一原请求前后台一致；不合并原请求身份，不把另一人的请求当作重放。
6. 证明仅减少“无证据变化时重复扫描”；证据合法变化后继续全量核验。按根增量投影留待需要时另行设计，本批不报告为已经实现。

**必须接受的时效变化：** 绕过合法 Action 且不提升 revision 的直接 SQL 篡改，在已有有效证明时可能无法被下一普通新请求立即发现；旧证明最迟按原扫描时刻 600 秒过期，之后的全量核验及独立审计会检查。明细/清偿/冲正/人工复核/独立审计不复用该证明。当前独立审计按批次派发，不能承诺每个用户固定五分钟内检出。实际合法写入、版本漂移和已置位的失效标志继续立即阻断旧证明。

如不接受此时效变化，替代方案是保留每个新请求全量核验，本批只优化同一原请求重复扫描及可证明的 SQL 开销，不宣称解决全历史增长成本。

## B3-03：停用账户的任务边界（推荐）

- 新认领先按原 owner→invoice→instance→task 锁定，核对任务/实例/账单归属；原 owner 已软删/匿名化则不认领、不增加 attempts、不发驱动请求。保留 pending 待核对，不将历史未执行工作误记成功。
- 已认领任务的结果仍属于原 user_id；仅 `ExecuteFulfillmentTaskAction` 结果提交与 `ExecuteServiceTaskAction::commit` 的历史用户锁使用 `withTrashed()`，保留原付款、租约、绑定和状态校验。原闭户通知抑制保持。
- 读取历史用户不授权新的采购、交付或资源控制；不修改全局 User 关系。外部调用前仍须原执行资格；外部结果到达后允许记录真实旧结果，不能转给复用邮箱的新账户。
- 正常注销已有 pending/running/业务阻断，本项处理历史/异常状态兼容，不能据此放宽注销条件。
